# SlicerRemoteView — Requirements

Status: v1, written by `architect` on 2026-10-17 from `prompts/00-goal.md` (Phase B), the decisions
D1–D7 confirmed by the user on 2026-10-17, and the research notes in `docs/research/` (`slicer.md`,
`relay.md`, `web.md`, `quest.md`). Maintained by `release` on `main` (see `docs/README.md`).
Milestones M0–M4 are defined in `docs/plan/00-overview.md`; the threat model lives in `docs/architecture.md`.

## 1. Purpose and scope

SlicerRemoteView lets a person working in 3D Slicer show the 3D scene (models and segmentations) live to
other people in the same room or elsewhere, on devices they already hold: a phone or tablet browser with no
installation, a Meta Quest headset in its browser (WebXR) or in a native app. The Slicer extension publishes
geometry as GLB plus small JSON state updates to a relay server on Railway; every device joins the session by
a 5-character code shown by Slicer, renders the geometry locally and follows the presenter's changes.

In scope for v1 (M0–M4): the Slicer extension (`SlicerRemoteView`, module `RemoteView`), the relay
(Node.js, in-memory sessions), the web viewer served by the relay, the Quest WebXR mode and the native Quest
app, one publisher and up to 20 read-only viewers per session with locally controlled cameras, and the
protocol contract shared by all components. Camera synchronisation, telepointer and device-initiated scene
changes are M4 stretch items; everything in section 6 is out of scope.

### Glossary

| Term | Meaning |
|---|---|
| Session | One live publication from one Slicer instance, identified by a code, held in relay memory with a TTL. |
| Code | 5 characters from the 31-symbol alphabet `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no `0 O 1 I L`), generated by the relay, unique among active sessions. |
| Publisher | The Slicer extension connected to a session; exactly one per session; the only party allowed to send geometry and state. |
| Viewer | A device (phone/tablet browser, Quest Browser, native Quest app) that joined a session with the code; read-only in v1. |
| Snapshot | A complete GLB of the currently exported scene (all nodes), tagged with a monotonic `sceneVersion`; the relay keeps only the latest one. |
| Update | A small JSON message changing state of existing nodes (visibility, color, opacity, transform) without re-sending geometry. |
| nodeId | Stable per-session identifier of a scene node: the MRML node ID for models (`vtkMRMLModelNode3`) or `<segmentationNodeID>/<segmentID>` for segments; stored in glTF node `extras.nodeId`. |
| Resume token | High-entropy secret issued to the publisher at session creation, used to re-attach to the same session after a disconnect. |
| Device profile | `mobile`, `quest2`, `quest3`: the decimation budget **chosen by the publisher** in the Slicer UI (protocol §7.5); viewers report their `platform` and an informational `profile` on join. |

## 2. Personas

**P1 — Clinician presenting a case.** A surgeon or radiologist in a hospital shows a segmented CT to
colleagues at a tumour board or explains an operation to a patient and family. Goal: in under a minute, have
everybody looking at the same anatomy on their own phones, rotating freely, while the clinician toggles
structures in Slicer. Constraints: hospital Wi-Fi behind NAT and a strict firewall (outbound HTTPS only, no
inbound ports, often an SSL-inspecting proxy), no admin rights to install software, patient data on screen
(GDPR), five minutes between cases, and the relay must never keep anything after the session ends.

**P2 — Medical student.** Joins from a personal iPhone or Android phone on mobile data or campus Wi-Fi, often
late, often with the phone locking or switching networks mid-session. Goal: understand spatial relations by
rotating, zooming, hiding and fading structures without being told how. Constraints: no app install, small
screen, limited memory (iOS kills heavy tabs), does not know the URL and will type the code from a projector
or scan a QR code; in labs the phone or tablet may be a shared departmental device.

**P3 — Course instructor (XR in medicine).** Runs a class of up to 20 students with a mix of phones and
Quest 2/3/3S headsets owned by the department, some shared between groups. Goal: start one session, put the
code on the projector, have everybody connected within two minutes, and switch cases during the class.
Constraints: university network with per-device rate limits, headsets without accounts of the students,
Quest 2 performance ceilings, strict class schedule (a failed join costs teaching time), and a need to
demonstrate both the WebXR path and the native app.

## 3. User stories

### P1 — Clinician

**US-01 Start a session and show the code.** As a clinician I want to click "Start session" in Slicer and see
a large code and a QR code so that people in the room can join without me dictating a URL.
- Given Slicer with a loaded scene and internet access, when I click Start session, then within 3 s the panel
  shows a 5-character code in a font readable from 2 m and the connection status "Live".
- Given the session is live, when I look at the panel, then a QR code encoding `https://<host>/j#<CODE>` is
  shown next to the code and a "Copy link" button copies the same URL.
- Given no network, when I click Start session, then an error explains that the relay is unreachable and
  offers Retry; nothing is sent elsewhere.

**US-02 Viewers follow my changes.** As a clinician I want visibility, colour, opacity and transform changes
I make in Slicer to appear on all viewers so that I can guide the discussion from my workstation.
- Given 3 connected viewers, when I hide a segment in Slicer, then it disappears on every viewer within 500 ms.
- Given a viewer has hidden a node locally, when I change that node's colour, then the colour change is
  stored and visible when the viewer shows the node again; its local hide is not overridden.
- Given I move a model with a linear transform, when I release the mouse, then viewers see the new pose within
  500 ms without re-downloading geometry.

**US-03 Session ends with Slicer.** As a clinician I want the session to end when I close Slicer or click Stop
so that nobody can keep looking at the patient's anatomy afterwards.
- Given a live session, when I click Stop session or close Slicer, then all viewers receive "Session ended"
  within 5 s and the relay frees the scene from memory.
- Given a live session and Slicer crashes, when the publisher grace period (120 s) passes without resume,
  then the relay deletes the session and viewers show "Session ended".

**US-04 No patient identifiers leave Slicer.** As a clinician I want to check what will be sent and hide node
names so that the export carries no PHI.
- Given a scene whose node names contain a patient name, when I open Start session, then I see the list of
  nodes to be exported with their names and a "Hide node names" option.
- Given "Hide node names" is on, when viewers list nodes, then they see generic labels (`Model 3`, `Segment 7`,
  … as in protocol §7.3) while nodeIds and colours still work.
- Given any export, when I inspect the GLB, then it contains no DICOM tags, file paths, MRML attributes or
  scene metadata beyond names, colours, opacity, visibility and transforms.

**US-05 Survive a network hiccup.** As a clinician I want Slicer to reconnect and keep the same code so that I
do not have to re-announce it when the hospital Wi-Fi drops for a few seconds.
- Given a live session, when the connection drops for 30 s, then Slicer reconnects automatically with the
  resume token and the code shown on the projector stays valid.
- Given the relay was redeployed and the session is gone, when Slicer reconnects, then it re-creates the
  session asking for the same code, which succeeds if the code is free, and re-sends the snapshot.

### P2 — Student

**US-06 Join by typing the code.** As a student I want to open the viewer page and type the code so that I
can see the scene on my phone without installing anything.
- Given the viewer page, when I type 5 characters (any case), then the input uppercases them and enables Join
  only when all characters are in the alphabet.
- Given a valid live code, when I press Join, then the model is visible within 10 s on 4G for a 10 MB scene,
  with a progress indicator while downloading.
- Given a valid code, when the page loads, then the code is never sent in the URL path or query string.

**US-07 Join by QR code.** As a student I want to scan the QR code on the projector so that I join in one tap.
- Given the QR on screen, when I scan it with the stock camera app, then it opens `https://<host>/j#<CODE>`
  and the viewer joins automatically.
- Given the page joined via fragment, when I look at the address bar or history, then the code has been
  removed (`/j`), so screenshots and shared tabs do not leak it.
- Given the fragment code is invalid, when the page loads, then I am shown the code entry with an error.

**US-08 Rotate, zoom, pan.** As a student I want natural touch controls so that I can inspect the anatomy.
- Given a loaded scene, when I drag with one finger, then the model orbits around the scene centre.
- Given a loaded scene, when I pinch or drag with two fingers, then the camera zooms or pans respectively,
  and the page itself does not zoom or scroll.
- Given no interaction for 2 s, when the camera has settled, then the viewer stops rendering frames.

**US-09 Toggle visibility locally.** As a student I want to hide and show structures on my device so that I
can isolate what I am studying without affecting others.
- Given the node list, when I tap a node's eye icon, then it hides on my device only, within one frame.
- Given a node I hid locally, when the presenter hides and shows it, then the presenter's state is applied and
  my local override is cleared with a short notice.

**US-10 Change opacity locally.** As a student I want to fade a structure so that I can see what lies behind.
- Given the node list, when I move a node's opacity slider, then the rendered opacity follows within one frame.
- Given opacity below 1, when other opaque nodes are present, then they remain correctly depth-sorted.

**US-11 Late join.** As a student who arrives late I want to see the current scene so that I do not miss
anything that happened before I joined.
- Given a session where the presenter already changed visibility and colours, when I join, then I receive the
  latest snapshot and the current state, and my view matches the presenter's within 10 s.
- Given the publisher is connected but has not sent a snapshot yet, when I join, then I see "Waiting for the
  presenter's scene" rather than an empty canvas.

**US-12 Reconnect after a network drop.** As a student I want the viewer to recover by itself so that locking
my phone or changing networks does not force me to re-enter the code.
- Given a joined viewer, when the connection drops, then the viewer shows "Reconnecting" and retries with
  exponential backoff (0.5 s to 30 s) without clearing the scene.
- Given the connection returns within the session TTL, when the viewer rejoins, then it is accepted without a
  new rate-limit penalty and shows the current state.
- Given the session has ended meanwhile, when the viewer rejoins, then it shows "Session ended" and stops.

**US-13 Wrong or expired code.** As a student I want clear feedback when a code does not work so that I know
whether to retype it or ask for a new one.
- Given a code that is malformed, unknown or belongs to an expired session, when I join, then the relay answers
  the same uniform `INVALID_CODE` (no session-existence leak) and I see "No session with this code" with the
  code echoed back and the input focused.
- Given I was already joined, when the session ends, then only I (an authenticated viewer) learn "This session
  has ended" via close `4001`/`4002`; unauthenticated clients never learn whether a code once existed.
- Given 10 failed attempts within a minute, when I try again, then I see "Too many attempts, wait N seconds".

**US-14 Join from Quest Browser (WebXR).** As a student with a Quest I want to open the viewer in the headset
browser and enter VR/passthrough so that I can look at the model at real scale without installing an app.
- Given the viewer page on Meta Quest Browser, when the scene is loaded, then an "Enter XR" button is shown
  and starts an `immersive-ar` (fallback `immersive-vr`) session.
- Given an XR session, when I use controllers or hands, then I can grab, rotate and scale the scene root.
- Given the scene exceeds the Quest 2 budget, when I enter XR, then a warning suggests the Quest profile.

**US-15 Join from the native Quest app and manipulate.** As a student I want to type the code in the native
app and grab the model with my hands so that the experience is comfortable for a whole class.
- Given the app's code keypad, when I enter a valid code, then the scene appears in front of me at 1.3 m,
  scaled 1:1 (1 mm in Slicer = 1 mm in the room).
- Given a loaded scene, when I grab it with one hand, then it follows my hand; with two hands I can rotate
  and scale it between 0.1x and 5x.
- Given the presenter hides a node, when the update arrives, then the node disappears in the headset within
  500 ms.

### P3 — Instructor

**US-16 Twenty students at once.** As an instructor I want 20 devices connected to one session so that the
whole class can follow the same case.
- Given a live session, when 20 viewers join within one minute, then all receive the snapshot and the panel in
  Slicer shows "20 viewers".
- Given 20 viewers, when a 21st tries to join, then it is refused with "Session is full" and the others are
  unaffected.
- Given 20 viewers, when I toggle visibility in Slicer, then all viewers update within 500 ms (p95).

**US-17 Pick a device profile for the class.** As an instructor I want to choose the Quest 2 budget so that
headset-heavy classes never hit performance problems.
- Given the Start session panel, when I select profile "Quest 2", then the export is decimated to at most
  500k triangles in total and the panel shows the resulting triangle count and GLB size.
- Given a connected Quest 2 viewer, when the session is on the default profile, then Slicer suggests switching
  to the Quest 2 profile.

**US-18 Switch cases during class.** As an instructor I want to load a new scene in Slicer without restarting
the session so that students keep the same code.
- Given a live session, when I close the scene and load another, then viewers show "Scene changed" and receive
  the new snapshot within 10 s; the code does not change.
- Given a new scene, when the previous nodes are gone, then viewers free the old geometry and their node list
  shows only the new nodes.

### 4.2 Relay server (`server`)

| ID | Requirement | Milestone | Source |
|---|---|---|---|
| FR-19 | The relay generates codes of 5 symbols from the 31-symbol alphabet with a CSPRNG, retrying until unique among active sessions. | M1 | non-negotiable |
| FR-20 | Sessions live only in process memory (`Map<code, Session>`), with idle TTL 30 min, hard lifetime 12 h and a sweep every <= 30 s; nothing is written to disk. | M1 | non-negotiable, D6 |
| FR-21 | The relay keeps a session alive while the publisher is connected; the idle TTL (`SESSION_TTL_S`, 1,800 s) counts only while no viewer is connected and is extended by `session.renew`; the relay warns with `session.expiring` 60 s before expiry (protocol §4.4). A connection is considered dead when no pong arrives before the next ping tick (relay WS ping 30 s; clients 15 s application ping with 10 s pong timeout, i.e. <= 25 s to detect). | M1 | non-negotiable |
| FR-22 | A session accepts exactly one publisher and at most 20 viewers; the 21st join is refused with `SESSION_FULL`. | M1 | D4, US-16 |
| FR-23 | The relay keeps the latest snapshot (one shared `Buffer`) and the current state per session and sends both to every viewer on join. | M1 | US-11 |
| FR-24 | The relay fans out snapshots and updates to all viewers of a session, skipping or coalescing for viewers whose `bufferedAmount` exceeds a high-water mark. | M1 | US-02, US-16 |
| FR-25 | Viewers may send only JSON messages <= 16 KiB; publisher JSON messages are capped at 256 KiB; binary frames from viewers and chunks > 1 MiB are rejected and the socket closed (1008 / 1009); snapshots > 64 MiB are refused with `PAYLOAD_TOO_LARGE` at `scene.snapshot.begin` (`docs/protocol.md` §3.3). | M1 | relay.md |
| FR-26 | Join attempts are rate limited per client IP (<= 10 per minute) and locked out (`RATE_LIMITED`, 10 min) after 20 failures in 10 min; a global failed-join counter raises a warning above 1,000 per hour. | M1 | non-negotiable |
| FR-27 | A publisher may resume a session within 120 s of disconnect by presenting the resume token; after a relay restart `session.create` honours the preferred code if free. | M2 | US-05 |
| FR-28 | The relay serves the web-viewer static files from the same origin, returns `index.html` for `/` and `/j`, and exposes `/healthz` without session data: relay-wide totals only (sessions, connected viewers; revised 2026-10-28 for the viewer's home page), no codes, tokens, IPs, scene data or session ids. | M1 | D6 |
| FR-29 | The relay never logs payloads, node names, codes or tokens (pino `redact`), logging only sizes, counts, durations, close codes and an internal session id. | M1 | non-negotiable |
| FR-30 | On SIGTERM the relay closes every socket with close code `4008` (relay restarting) so clients reconnect immediately, within the configured draining window. | M2 | relay.md |
| FR-31 | Codes, tokens and tickets travel only in WebSocket message bodies (or POST bodies), never in URL paths, query strings or cookies. | M1 | non-negotiable |
| FR-32 | `/metrics` is disabled by default and, when enabled, protected by a bearer token from the environment. | M4 | NFR-37 |
| FR-33 | Browser WebSocket upgrades with a foreign `Origin` header are rejected; absent `Origin` (Slicer, Quest) is allowed. | M2 | relay.md |
| FR-34 | The relay runs as a single replica with `--max-old-space-size-percentage=75`, enforcing the per-session snapshot cap (64 MiB, `PAYLOAD_TOO_LARGE`) and the aggregate budget (`MAX_TOTAL_SNAPSHOT_BYTES`, 512 MiB default, `CAPACITY` when exceeded). | M1 | D6, NFR-06 |

## 5. Non-functional requirements

## 6. Out of scope (v1)

- Video or pixel streaming of the Slicer render window (D1).
- Volume rendering, slice views, markups, DICOM transfer or any pixel data.
- More than one Slicer publisher per session, or merging sessions.
- User accounts, authentication beyond the code and tokens, SSO, audit trails.
- Persistence of sessions, scenes or history on the relay (memory + TTL only).
- WebXR on iOS/iPadOS Safari (not supported by the platform); AR Quick Look fallback.
- Editing geometry from devices (segment editing, measurements, annotations).
- Recording, replay or export of sessions from devices.
- Multi-replica relay, Redis, or horizontal scaling.
- Draco or meshopt compression (Draco may be added as an optional milestone after measurements).
- Camera synchronisation, telepointer and device-initiated visibility changes are not in M1–M3; they are M4 candidates, not commitments.

## 7. Assumptions and risks

### Assumptions

- A1 Hospital and university networks allow outbound HTTPS/WSS on port 443 to `*.up.railway.app` or the custom domain; SSL-inspecting proxies present a certificate chain trusted by the OS.
- A2 Presenters use Slicer 5.12.x with internet access on the same machine; no on-premises relay is required in v1.
- A3 A typical teaching scene after decimation is 5–20 MB GLB; whole-body segmentations are the exception handled by budgets and warnings.
- A4 Devices are personal or departmental, not kiosk-locked; the browser can open an HTTPS URL and scan QR codes.
- A5 The Railway EU region is available on the chosen plan; otherwise US regions are acceptable for transit-only data with a documented note.
- A6 Students and clinicians accept that the viewer is read-only in v1 and that cameras are independent.
- A7 The course team has at least one Quest 2 and one Quest 3/3S for device testing and a Mac with Apple Silicon for the Meta XR Simulator.

### Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R-01 | `wss://` with `ClientWebSocket` on IL2CPP/Android (Quest) fails on certificate trust or large frames; not documented by Unity. | Medium | High for M3b | Device smoke test against the Railway relay in the first `quest` sprint; fallback to NativeWebSocket or an HTTPS GET of the GLB with a one-time ticket; keep chunks <= 1 MiB. |
| R-02 | iOS Safari kills the tab under memory pressure on large scenes without any event. | Medium | High | `mobile` profile: recommended snapshot <= 32 MiB (20 MiB target for phones), quantized attributes, dispose and drop buffers, measure on real iPhones early (M1), show a warning before loading a large snapshot. |
| R-03 | Railway redeploy or crash drops all sessions mid-class. | High (every deploy) | Medium | Publisher resume with preferred code, viewer auto-rejoin, close code `4008` (relay restarting), 30 s draining, deploy outside class hours, single replica documented. |
| R-04 | Node.js 22 is in maintenance LTS (EOL 2027-04-30). | Certain | Low | Code uses no Node-22-only APIs; CI matrix adds Node 24; migrate before 2027. |
| R-05 | Large segmentations exceed triangle or size budgets, or decimation blocks the Slicer UI for minutes. | High | Medium | Per-node and total budgets, progress dialog, export only segments visible in 3D, process one node per timer tick, warn and suggest fewer segments. |
| R-06 | Extension Index requires explicit opt-in before sending any data; a streaming extension may be questioned at review. | Medium | Medium | No network at startup, explicit "Start session" with a consent text naming the relay host, "Hide node names", documentation of data flow in README. |
| R-07 | Unity CI licensing: Personal licence use in CI is undocumented; Unity Build Automation free minutes are limited. | Medium | Low | Treat Unity builds as manual/local until licensing is confirmed; keep EditMode tests runnable locally; budget a Pro seat if CI builds become necessary. |
