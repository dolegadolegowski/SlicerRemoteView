# Research — live scene changes from Slicer (SLC-29, SLC-31)

This note backs SLC-29 (the pure live-update controller, `remoteview_core/live.py`) and SLC-31 (the Slicer observers and their wiring), written on 2026-10-27 before either started. It answers four questions: which MRML events Slicer 5.12.4 fires for each user action on a model shown in a 3D view, which `Change` flag each event should mark (`remoteview_core/debounce.py`), and how a scripted module can observe them safely and then let go of them.

**Method.** Three research passes. An adversarial verifier re-derived every load-bearing claim from source. Claims that failed are given here in their corrected form. Claims that were never re-derived are marked `[TODO verify]`. The Python-binding behaviour was also probed with the VTK 9.6.2 wheel in `slicer-plugin/.venv` (scratch scripts, not kept). Nothing ran inside Slicer (CLAUDE.md rule 10). The manual steps will be `docs/testing/slicer.md` §6 (SLC-31).

**Citations.** Unprefixed paths are in the Slicer v5.12.4 tree (git `4e21c19`). `Core/` is short for `Libs/MRML/Core/`. `VTK/` is the Slicer/VTK fork at `c9cd17a` that 5.12.4 builds by default: `CMakeLists.txt:447, 455` and `SuperBuild/External_VTK.cmake:172-175`. The cited VTK files are byte-identical to upstream VTK v9.6.2. `CPython/` is v3.12.10 (`CMakeLists.txt:216-217`). `PythonQt/` is commontk/PythonQt `74dcd675`. `CTK/` is CTK `5056664a`.

## 2. Event table: user action → events → emitter → `Change` flag

Abbreviations: DME = `DisplayModifiedEvent`, TME = `TransformModifiedEvent`, MME = `MeshModifiedEvent`. "Deferred" means the event goes through `InvokeCustomModifiedEvent`. While the node's `DisableModifiedEvent` flag is set (by `StartModify`, `MRMLNodeModifyBlocker` or `SetDisableModifiedEvent(1)`), such an event is only counted. At the outermost `EndModify` it is invoked **once, with callData NULL**, after the node's own `ModifiedEvent`, in ascending event-id order (`Core/vtkMRMLNode.h:357-379, 569-579, 588-617, 631-644`; direct flag use at `Core/vtkMRMLScene.cxx:2221-2251` and `Core/vtkMRMLNode.cxx:1206-1208`). The emitter is always the **model node** unless the row says otherwise. Identify the node from `caller` and never from callData.

## 3. Folders and views

- Folder display changes reach the models through the models' own DME (row 4). No folder observer is needed. The Data-module tree wraps eye toggles on items with more than 10 children in its own batch (`qMRMLSubjectHierarchyTreeView.cxx:826-848`).
- A folder rename also fans out to the branch, because `SetItemName` calls `DataNode->SetName` (`Core/vtkMRMLSubjectHierarchyNode.cxx:2173-2181`). Expect `APPEARANCE` bursts that `classify` reduces to an empty plan.
- Reparenting is notified only by hidden or applying folders (row 5). The visible, non-applying folder with opacity ≠ 1 is a known gap. Observing the SH node's `SubjectHierarchyItemReparentedEvent` (`@vtk.calldata_type(vtk.VTK_LONG)`, `Docs/developer_guide/script_repository/subjecthierarchy.md:87-100`) would close it. Whether Slicer's own 3D view also stays stale in that case is `[TODO verify]`; the model displayable manager does not observe the SH node.
- View nodes: mark every watched model `APPEARANCE` when a `vtkMRMLViewNode` is added or removed, because what the 3D view shows depends on the view list (row 17; `Core/vtkMRMLDisplayNode.cxx:661-664`).

## 4. Close, import and batch processing

- `CloseState`, `ImportState` and `RestoreState` include the `BatchProcessState` bit (`Core/vtkMRMLScene.h:612-615`). `SaveState`, `UndoState` and `RedoState` do not (:616-618). `StartState` fires `StartBatchProcessEvent` only on entry from no batch, and before the state's own start event (`Core/vtkMRMLScene.cxx:730-744`). `EndState` fires the state's own end event first and `EndBatchProcessEvent` only when the last batch-implying state ends (:747-773). **So observing Start/`EndBatchProcessEvent` alone gives one balanced hold per outermost batch, and `EndCloseEvent` always arrives inside it.** The Import events are redundant. `ProgressImportEvent` has the same numeric value as `EndImportEvent` (`Core/vtkMRMLScene.h:722-723`) and must never be observed. The header's example at :671 wrongly says `EndState(Import)` fires `StartBatchProcessEvent`.
- **Attach in the middle of a batch.** If observers are attached while `scene.IsBatchProcessing()` (`Core/vtkMRMLScene.h:1047-1049`), the first batch event seen would be an unmatched `EndBatchProcessEvent`. Call `hold()` at attach in that case. This can plausibly happen: `qSlicerIOManager` shows a window-modal progress dialog while loading (`Base/QTGUI/qSlicerIOManager.cxx:94-107, 489`). Whether its `setValue` runs `processEvents` is `[TODO verify]`, and so is whether `IsBatchProcessing` is wrapped for Python.
- **Holds must be counted.** `EndBatchProcessEvent` observers may start nested batches during the same dispatch; for example the SH plugin logic observes it at priority 10 (`qSlicerSubjectHierarchyPluginLogic.cxx:192`). `Debouncer` keeps **one** hold counter and ignores a release only at zero (`debounce.py:154-167`). Its other holds (snapshot in flight, `GRACE`) need the live controller to count batch holds itself.
- **Reset timing** (`debounce.py:149-199`). Outside a hold and the release hand-off, `reset()` flushes after min(150, 250 − ms since the first unflushed mark). During the 0 ms hand-off it flushes at 0 ms. A slow mark after it extends the wait to 750 ms (at most 2 s). A scene close always resets inside the batch hold, so it flushes at 0 ms on `EndBatchProcessEvent`, or later if the in-flight or pause hold is still on.
- During `Connect`, `ResolveSubjectHierarchy` runs after `EndBatchProcessEvent` (`Core/vtkMRMLScene.cxx:814`). Its events land before the 0 ms flush and are harmless.

## 5. Threading and re-entrancy

- MRML is main-thread only by Slicer convention (`docs/research/slicer.md` §3 [S23][S24]). The MRML event broker is synchronous by default (`Core/vtkEventBroker.cxx:97`). It is `[TODO verify]` that VTK runs a Python callback on whichever thread invokes the event, taking the GIL itself, and that worker requests are replayed on the main thread by `vtkSlicerApplicationLogic`. Callbacks therefore keep a cheap guard: an event seen off the main thread only sets a flag, which the pump turns into a full re-export.
- `vtkMRMLNode::MRMLCallback` silently **drops** an event that reaches a node while that node is already inside its own `ProcessMRMLEvents` (`Core/vtkMRMLNode.cxx:1114-1135`, guard at 1124-1128). A handler that changes MRML synchronously can make other observers miss changes. **Handlers only mark**: no MRML writes, no exports, no `GetMesh()` (which runs `producer->Update()`: `Core/vtkMRMLModelNode.cxx:240-258`), no `GetDisplayNode()` in `NodeAddedEvent`.
- Exports and `classify` run from the debouncer's single-shot timer, from the event loop and never inside an MRML event. The last release starts it at 0 ms (`debounce.py:159-167`). Reads made during a flush can still fire events synchronously: a lazy display-reference resolution fires DME (row 2). Such a mark starts a fresh debounce window (`debounce.py:169-177`). A resolution happens once, so this gives at most one extra flush. Whether `Update()` of a trivial producer can fire MME back is `[TODO verify]`; manual §6 has an "idle → exactly one snapshot" step that would catch a loop.
- VTK's `InvokeEvent` allows observers to be added or removed during dispatch. It is `[TODO verify]` that an observer added during a dispatch is not called for that same event. Either way the node's later events are separate dispatches, so observing a new model inside `NodeAddedEvent` catches its mesh and display events.

## 6. Exceptions and privacy (T7)

An exception other than `KeyboardInterrupt`/`SystemExit` that escapes a Python observer goes to `PyErr_Print` (`vtkPythonCommand.cxx:223, 237`). From there:

- **Traceback printed.** The default `sys.excepthook` prints the message, notes and chained exceptions, but not local variables (`CPython/Python/pythonrun.c:783-852`). No Slicer, CTK or PythonQt file overrides the hook.
- **Console, terminal and log file.** PythonQt has replaced `sys.stderr` (`PythonQt/src/PythonQt.cpp:1854-1869, 1907-1918`, signal at 1793-1800). The text reaches:
  - the Python console (`CTK ctkPythonConsole.cpp:660-661`);
  - `std::cerr` (`CTK ctkAbstractPythonManager.cpp:66, 152-153, 736-739`), which Slicer captures into the error log and the log file as a Critical entry (`CTK ctkErrorLogStreamMessageHandler.cpp:98-99, 221`; `Base/QTGUI/qSlicerApplication.cxx:342, 365, 426, 1108-1112`).
- **Kept in the interpreter.** It is also kept in `sys.last_exc`/`last_traceback`, frames included (`pythonrun.c:797-811`).
- **Nothing reaches the caller.** The exception never propagates to the code that fired the event. A `try` at the call site does not help.
- **Qt slots and `QTimer` callbacks.** They go through `PythonQt::handleError` → `PyErr_Print` (`PythonQtSignalReceiver.cpp:130-136`; `PythonQt.cpp:1697-1708`) and leak the same way.

Exception texts often quote a node ID (`KeyError(node_id)`), and names may carry PHI. **Every Python callable that C++ enters must wrap its whole body in `except Exception` and log only `type(exc).__name__`**, never with `exc_info`/`logging.exception`. That means every VTK/MRML observer, the flush timer's slot and the pump. Never raise or forward `SystemExit`/`KeyboardInterrupt`: both end the process (`vtkPythonCommand.cxx:232-235`; `pythonrun.c:773-786`).

## 7. Observer recipe for a scripted module

```python
import threading
from vtkmodules.util.misc import calldata_type          # == vtk.calldata_type
from vtkmodules.vtkCommonCore import VTK_OBJECT, vtkCommand

MODEL_CLASS = "vtkMRMLModelNode"

class SceneWatcher:
    def attach(self):
        e = self._events                                   # event ids passed in from slicer.vtkMRML* constants
        for event_id, method in ((e.node_added, self._on_node_added), (e.node_removed, self._on_node_removed),
                                 (e.start_batch, self._on_start_batch), (e.end_batch, self._on_end_batch),
                                 (e.end_close, self._on_end_close)):
            self._scene_tags.append(self._scene.AddObserver(event_id, method))   # own tags, one callable per event
        if self._scene.IsBatchProcessing():                # attached mid-batch: its End must find a hold
            self._sink.hold()
        for node in self._nodes_by_class(MODEL_CLASS):
            if node.GetClassName() == MODEL_CLASS:         # exact class, hidden ones too (shown later → marked)
                self._watch(node)

    def _watch(self, node):                                # DME, MME, TME, ModifiedEvent; caches: name, HFE, matrix
        ...

    @calldata_type(VTK_OBJECT)                             # in the class body only; never set CallDataType by hand
    def _on_node_added(self, caller, event, calldata=None):   # 2 args when callData is NULL
        self._guard(self._added, calldata)

    def _on_display(self, caller, event):                  # undecorated: the node is `caller`, never callData
        self._guard(self._mark_unless_hidden_from_editors, caller, Change.APPEARANCE)

    def _guard(self, fn, *args):
        if threading.get_ident() != self._main_thread:
            self.off_thread = True                         # the pump asks for a full snapshot
            return
        try:
            fn(*args)
        except Exception as exc:                           # VTK would print the traceback (T7)
            _log.error("scene observer failed (%s)", type(exc).__name__)
```

Rules:

1. Observe the scene for `NodeAddedEvent`, `NodeRemovedEvent`, `StartBatchProcessEvent`, `EndBatchProcessEvent` and `EndCloseEvent`. Only the two node events are decorated. Never decorate the state handlers.
2. Observe every exact-class model node for DME, MME, TME and `ModifiedEvent`. Slicer's model displayable manager observes the same Mesh/Display/Transform set (§8). Do not observe display nodes; the model's DME covers all of them (rows 1-4).
3. In the mesh, display and transform handlers, return early when `caller.GetHideFromEditors()` is true. Slice-plane models are exact-class and hidden from editors, and are reported to fire MME on every slice move `[TODO verify]`.
4. **`ModifiedEvent`.** Compare `GetName()` with the cache and mark `NAME` only when it changed and the node is not hidden from editors. Mark `APPEARANCE` when `GetHideFromEditors()` flipped.
5. **TME.** Read the linear RAS world matrix with the same adapter call collect uses (`MrmlSceneApi.world_matrix`, which returns `None` for a non-linear chain). Mark nothing when it equals the cached matrix, since parent renames fire TME (row 7). Always mark for a non-linear chain. Whether `GetMatrixTransformToWorld` can itself fire events is `[TODO verify]`.
6. **`NodeAddedEvent`.** An exact-class model is watched at once, and marked `ADDED` unless hidden from editors. A view node marks every watched model `APPEARANCE`.
7. **`NodeRemovedEvent`.** A watched model gets `REMOVED` and its tags are removed. The node object is still valid during the event (`Register` at `Core/vtkMRMLScene.cxx:1550`, `UnRegister` at :1586).
8. **Batch and close events.** `StartBatchProcessEvent` → `hold()`, `EndBatchProcessEvent` → `release()`, `EndCloseEvent` → `reset()`.

## 8. Slicer's own 3D view does the same

Corrected after verification.

- **What it observes.** `vtkMRMLModelDisplayableManager` adds broker observations for MME, DME, TME and `ClipNodeModifiedEvent` on **every non-slice displayable node**, not only models (`Libs/MRML/DisplayableManager/vtkMRMLModelDisplayableManager.cxx:583-662, 1047-1074`). It never observes display nodes and reads DME's callData (:356-368).
- **The clip observation is dead.** Only `vtkMRMLClipNode` fires `ClipNodeModifiedEvent` (`Core/vtkMRMLClipNode.cxx:351, 362, 373, 480, 617`), so clip changes arrive as DME instead (row 1). `RemoveDisplayableNodeObservers` never removes the clip observation (:1238-1251).
- **Scene events.** It observes Start/End BatchProcess, Close, Import and Restore, plus NewScene, NodeAdded and NodeRemoved (`vtkMRMLAbstractDisplayableManager.cxx:693-711`). Only the NodeAdded/NodeRemoved handlers check `IsBatchProcessing()` (:432-435, 452-455). Node events are **not** gated during a batch (:334-383). The catch-up runs at `EndBatchProcessEvent` → `UpdateFromMRMLScene` (`Libs/MRML/Logic/vtkMRMLAbstractLogic.cxx:481-484`).
- **VR view.** SlicerVirtualReality@`c9179edf` instantiates the same manager in its VR view (`VirtualReality/Widgets/qMRMLVirtualRealityView.cxx:357-391`).

## 9. Cleanup and lifetime

- Remove each node's tags at its `NodeRemovedEvent`. Remove everything on Stop, at session end and in the widget's `cleanup()`. After `EndCloseEvent` no watched model is left, because `RemoveAllNodes` removed every model through `NodeRemovedEvent` (row 13).
- `VTKObservationMixin` keys observations by callable object. With per-event callables, removing one needs the same object. It is `[TODO verify]` that its `removeObserver` keeps the node referenced until `removeObservers()`. Our own tag bookkeeping avoids both issues.
- The flush runs on an owned single-shot `qt.QTimer` (`setSingleShot(True)`, `connect('timeout()', slot)`, `start(msec)`, `stop()`), stopped and disconnected in `cleanup()`. That PythonQt maps `start(int)` and `setSingleShot` is `[TODO verify]` in Slicer.
