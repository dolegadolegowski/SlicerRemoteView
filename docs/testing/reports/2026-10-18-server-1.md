# Verify how the Railway edge sets `X-Forwarded-For` (relay trusts exactly one proxy hop)

- **Reported by**: server (`ws/server`, commit `00409d4`, SRV-02)
- **Affects**: deploy — DEP-06 first-deploy checklist (`docs/deploy.md`); release — wording in ADR 0008 §6a and
  `docs/architecture.md` §9
- **Severity**: medium
- **Milestone**: M1
- **Protocol**: v1.0 §12 (per-IP limits); `docs/architecture.md` §8 T1, T3; §9 `TRUST_PROXY` `[TODO verify]`
- **Status**: triaged (D6: neutral wording in PRO-20; hop count after DEP-06; release: 2026-10-27-protocol-4)

## Steps to reproduce

1. Deploy the relay (`TRUST_PROXY` unset = `true`).
2. From a client, send a request with a forged header, e.g.
   `curl -H 'X-Forwarded-For: 6.6.6.6' https://<relay>/healthz`, and with no header.
3. Observe which address the relay treats as the client IP (once SRV-08 exists: its HMAC'd key changes per
   client, or a temporary debug build that logs `request.ips.length` only — never the addresses themselves).

## Expected

With `TRUST_PROXY=true` the relay (SRV-02) trusts **only its immediate peer**: `request.ip` is the last
`X-Forwarded-For` entry, i.e. the one the Railway edge added. This is correct if the edge connects directly to
the container (one internal hop) — whether it replaces or appends to the header. The forged `6.6.6.6` must not
become the client IP.

## Actual

Not verified yet: Railway's documentation does not say whether there is more than one internal proxy hop. If
there are two or more, every client would appear as the address of the inner proxy, and all users would share
one per-IP rate-limit bucket (SRV-08).

## Notes / suspected cause

If the check shows more than one hop, the relay needs a hop count or a trusted-proxy list instead of the boolean
`TRUST_PROXY` (server task; please file the result here). Fastify 5.12.7 treats a numeric `trustProxy` as
"fail closed" (socket address), so the fix is a trust function, not a number.

## Documentation (for `release`)

ADR 0008 (Context and Decision 6a) and architecture §9 say "`trustProxy: true`". In Fastify that trusts **every**
hop, so `request.ip` would be the left-most `X-Forwarded-For` entry, which a client can forge. The relay
implements `TRUST_PROXY=true` as "trust only the immediate peer" (`trustProxy: (address, hop) => hop === 0`,
`relay-server/src/app.ts`). Please add an erratum to ADR 0008 §6a and clarify the `TRUST_PROXY` row of
architecture §9 accordingly; the relay workstream cannot edit those files (CLAUDE.md rule 4).
