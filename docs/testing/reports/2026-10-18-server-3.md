# Threat model T1: `session.create{preferredCode}` reveals whether a code is live

- **Reported by**: server (`ws/server`, commit `65145a3`, SRV-04 review)
- **Affects**: release — `docs/architecture.md` §8 (T1 residual risk); server — SRV-08 (mitigation)
- **Severity**: low
- **Milestone**: M1
- **Protocol**: v1.0 §4.1 (`preferredCode` granted only when free, else a fresh code "silently"), §12
- **Status**: fixed (SRV-08: every `preferredCode` counts as a failed join; see `2026-10-20-server-1.md` item 3)

## Steps to reproduce

1. Connect as a publisher and send `session.create{preferredCode: "<guess>"}`.
2. Compare `session.created.code` with the guess.

## Expected

Guessing live codes is bounded by the per-IP join limits of §12 (10 `viewer.join{code}`/min, ban after 20
failures in 10 min) — architecture §8 T1 computes the residual risk from that rate.

## Actual

A refused `preferredCode` (live, or released less than `CODE_QUARANTINE_S` ago) tells the caller that the code
is (or just was) in use. These probes are limited only by `session.create` 5/min/IP and do not count toward
the join-failure ban, so they are roughly 5× faster than sustained `viewer.join` guessing for one IP. They
reveal liveness, not scene content (joining still needs a successful `viewer.join`).

## Notes / suspected cause

Mitigation in the server plan (follow-up recorded in `docs/plan/server.md`, to be folded into SRV-08): a
`session.create` whose well-formed `preferredCode` is not granted counts as a failed join for the IP's failure
and ban counters. `release`: please mention this vector in T1 of architecture §8. No protocol change is needed.
