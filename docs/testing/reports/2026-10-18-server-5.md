# Protocol §9.3 wording of close `4012` vs the relay's handshake timer

- **Reported by**: server (`ws/server`, commit `16be471`, SRV-05 review)
- **Affects**: protocol — `docs/protocol.md` §3.1 and §9.3 (wording only, no behaviour change for clients)
- **Severity**: low
- **Milestone**: M1
- **Protocol**: v1.0 §3.1, §4.3, §9.3
- **Status**: triaged (PRO-20)

## Steps to reproduce

1. Connect to `/ws` and send a first message that fixes a role but never completes the handshake, e.g. a
   `session.create` without `profile` (answered `INVALID_MESSAGE`), and nothing else.

## Expected (by the current wording)

§9.3: `4012` = "handshake timeout (no first message in 10 s)"; a socket that sent any first message would stay
open.

## Actual

The relay (SRV-05) closes `4012` when no session is **bound** to the socket 10 s after the upgrade — a created,
resumed or joined session ends the timer, a merely role-fixing first message does not. This bounds idle
unauthenticated sockets (T3) and is the same rule §4.3 needs after `SESSION_NOT_FOUND` ("keeps the socket open
for 10 s" for a fallback `session.create`, closed `4012` otherwise — SRV-15 re-arms the timer at that reply).
A conforming client never notices the difference.

## Notes / suspected cause

Suggested clarification for §9.3 (protocol workstream, `docs(protocol)` commit per CLAUDE.md rule 2): "`4012` —
no session bound within 10 s of the upgrade (or of a `SESSION_NOT_FOUND` reply to `session.resume`)".
