# `parseEnvelope` issues can carry sender-chosen keys in `instancePath`

- **Reported by**: server (`ws/server`, commit `392aaac`, SRV-23 review)
- **Affects**: protocol — `shared/ts/validate.ts` (`toIssues`, module comment "safe to log or echo")
- **Severity**: low
- **Milestone**: M1
- **Protocol**: v1.0 §9.2 (`details` MUST NOT contain codes, tokens or scene content)
- **Status**: open

## Steps to reproduce

1. `parseEnvelope('{"protocolVersion":"1.0","type":"viewer.count","viewerCount":1,"viewerLimit":20,'
   + '"platforms":{"<any text>":-1}}')`.

## Expected

The module comment of `validate.ts` says errors "never return the offending values … so the result is safe
to log or echo in `error.details`".

## Actual

`error.instancePath` (and `issues[].instancePath`) is `/platforms/<any text>`: for schemas with
`additionalProperties`/maps (`viewer.count.platforms`), Ajv puts the sender-chosen **key** into the JSON Pointer,
unbounded in length. Values never appear, keys can.

## Notes / suspected cause

The relay is not affected today: it judges a known type outside the sender's role as `UNAUTHORIZED` before
looking at its schema errors, client→relay schemas have no sender-keyed maps, and it caps the echoed
`instancePath` at 128 characters (SRV-23). Suggested fix in `shared/` (protocol workstream): in `toIssues`,
replace pointer segments below an `additionalProperties`/`patternProperties` location with `*` (or cap their
length) and adjust the comment, so other receivers (web-viewer, quest-app) cannot log client- or relay-chosen
keys by trusting it.

## Related: messages before the session handshake completed (protocol §2, §3.1, §11)

Also for the protocol workstream (SRV-23 review): after a handshake message that did not bind a session (a
schema-invalid `session.create`, or the `SESSION_NOT_FOUND` fallback window of §4.3), the relay accepts only
handshake messages and `ping`. Anything else — an allowed type such as `scene.update`, and also an unknown type —
is an `UNAUTHORIZED` offence (the second closes `1008`), whereas §2 alone would answer an unknown type with
`UNSUPPORTED_TYPE` and keep the socket open. Suggested §3.1 sentence: "until `session.created`, `session.resumed` or
`viewer.joined`, only handshake messages and `ping` are accepted; anything else is an `UNAUTHORIZED` offence".
