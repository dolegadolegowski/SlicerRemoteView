# T11 wording vs `session.publisherState`, and the answer for a just-ended code

- **Reported by**: server (`ws/server`, commit `47878aa`, SRV-06 review)
- **Affects**: protocol — `docs/protocol.md` §4.6, `shared/schema/session.publisherState.schema.json`; release —
  `docs/architecture.md` §3 (code lifecycle) and §8 (T11)
- **Severity**: low
- **Milestone**: M1
- **Protocol**: v1.0 §4.6, §9.2, §12
- **Status**: triaged (PRO-20: no `sessionId` field; T11 narrowed by release, 2026-10-27-protocol-4)

## Steps to reproduce

1. Compare architecture §8 T11 ("`sessionId` in every relay→client control message so clients drop mismatches")
   with protocol §4.6 and the `session.publisherState` schema (no `sessionId` field).
2. Compare architecture §3 ("a viewer who types a code from a just-ended session gets `SESSION_NOT_FOUND`") with
   protocol §9.2 (`SESSION_NOT_FOUND` is for `sessionId`/token lookups), §12 (uniform `INVALID_CODE` for failed
   joins) and the SRV-06 criterion "a subsequent `viewer.join` with that code → `INVALID_CODE`".

## Expected

The threat model, the contract and the plan agree.

## Actual

- `session.publisherState` carries no `sessionId`, so viewers cannot drop a misrouted one as T11 promises. The
  relay sends exactly what the contract defines (SRV-06); its fan-out only iterates the session's own viewers, and
  a two-session isolation test covers it.
- Architecture §3 names `SESSION_NOT_FOUND` for a quarantined code; the protocol and the plan say `INVALID_CODE`.
  The relay will answer `INVALID_CODE` (SRV-07), uniform with unknown and malformed codes, so that responses do
  not reveal which codes were recently live (§12).

## Notes / suspected cause

Suggestions: protocol — add an optional `sessionId` to `session.publisherState` (additive, 1.x; the relay will
then fill it), or narrow the T11 wording; release — change architecture §3 to `INVALID_CODE`.
