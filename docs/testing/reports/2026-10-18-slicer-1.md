# ADR 0005 §4 and research note print the RAS→glTF matrix `C` transposed

- **Reported by**: slicer (`ws/slicer`, SLC-05, on top of `fef6159`)
- **Affects**: release / architect — `docs/adr/0005-slicer-glb-export-coordinates-and-node-ids.md` §4 (line 52),
  `docs/research/slicer.md` §4 "Coordinate systems and units" (lines 288–291)
- **Severity**: medium (documentation; anyone implementing the conversion from the matrix literal puts superior at −Y
  and anterior at +Z)
- **Milestone**: M1
- **Protocol**: v1.0 §7.1 (normative: `[x, y, z]_gltf = [R, S, -A] × 0.001`)
- **Status**: open

## Steps to reproduce

1. Take `C = 0.001·[[1,0,0],[0,0,-1],[0,1,0]]` as printed in ADR 0005 §4 (and in the SLC-05 row of
   `docs/plan/slicer.md` before this run) and apply it, row-major as numpy/most code does, to the RAS point
   `(R, A, S) = (10, 20, 30)` mm.

## Expected

`(0.010, 0.030, -0.020)` m — protocol §7.1 and the PRO-08 fixture `shared/fixtures/glb/asymmetric-2nodes.glb`
(RAS (0,100,0) anterior → glTF (0,0,−0.1)).

## Actual

`(0.010, -0.030, 0.020)` m: the literal is the **transpose** of the contract matrix. It equals the column-major listing
of SlicerOpenAnatomy's root matrix `[s,0,0,0, 0,0,-s,0, 0,s,0,0, 0,0,0,1]` read as rows. Both have determinant +1, so a
winding check does not catch it.

## Notes / suspected cause

The slicer workstream implements `C = 0.001·[[1,0,0],[0,0,1],[0,-1,0]]` (rows act on `(R, A, S)`), pinned by asymmetric
tests and a consistency check against the PRO-08 fixture (`slicer-plugin/tests/test_coords.py`), and corrected its own plan
row. Suggested fix for `release`: an erratum in ADR 0005 and a note in the research file stating the row-major matrix
`C = 0.001·[[1,0,0],[0,0,1],[0,-1,0]]` (rows act on `(R, A, S)`). The transposed literal is the inverse map (glTF → RAS);
applied as RAS → glTF it rotates the scene 180° about x (upside down, front and back swapped).
Web/Quest are unaffected as long as they consume glTF as-is (no RAS math on their side).
