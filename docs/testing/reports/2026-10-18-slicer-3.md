# "Hide node names" does not cover a segment ID derived from a name

- **Reported by**: slicer (`ws/slicer`, SLC-01 security review, commit `6393692`)
- **Affects**: protocol — `docs/protocol.md` §7.3 (`nodeId` = `<segmentationNodeID>/<segmentID>`); slicer — SLC-07/SLC-13
- **Severity**: medium (raised from low by the `ws/slicer` branch audit: `anonymizedNames: true` is written while a
  name-derived segment ID still leaves Slicer; see also `2026-10-19-slicer-3.md`)
- **Milestone**: M2
- **Protocol**: v1.0 §7.3, threat model T7
- **Status**: in progress (SLC-27: alias registry and writer rules; the segment export itself SLC-35–SLC-37)

## Steps to reproduce

1. Create a segmentation whose segment IDs were set explicitly from names (importers/scripts can do this; scenes
   from older Slicer versions may carry such IDs). Current Slicer generates random IDs when none is given
   (`vtkSegmentation::GenerateUniqueSegmentID`, Slicer `main`) `[TODO verify for 5.12.4 and for DICOM SEG import]`.
2. Enable "Hide node names" and share the scene.

## Expected

No name-derived text leaves Slicer (NFR-16, T7).

## Actual

`extras.name` becomes `Model <n>`/`Segment <n>`, but `nodeId`/`extras.segmentId` keep the segment ID verbatim.

## Notes / suspected cause

The slicer workstream will measure this in manual §5 (SLC-13). If real, a protocol-compatible option is to map
segment IDs to opaque per-session aliases in the publisher when names are hidden (the `nodeId` stays stable for the
session; §7.3 only requires stability for the scene's lifetime) — needs a protocol note from `protocol`/`release`.
