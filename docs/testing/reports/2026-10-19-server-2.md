# Viewer entries are capped per session; interim answer to a token rejoin

- **Reported by**: server (`ws/server`, SRV-07 review)
- **Affects**: release — `docs/architecture.md` §3 (`Viewer` entry "kept until session ends"); web, quest —
  information only (rejoin path until SRV-15)
- **Severity**: low
- **Milestone**: M1
- **Protocol**: v1.0 §5.1, §9.2, §12
- **Status**: open

## Steps to reproduce

1. Join a session with its code and leave again, 61 times, with `MAX_VIEWERS` = 20.
2. Rejoin with the `viewerToken` of the first viewer (once SRV-15 is in).

## Expected

Architecture §3: a viewer entry, and with it its token, is "kept until session ends", so every token
rejoins for the whole session (ADR 0008 errata).

## Actual

The relay keeps at most `3 × MAX_VIEWERS` entries per session. Beyond that it drops the oldest
**disconnected** entry and its token. Connected viewers are never dropped. Without this cap, anyone holding the
code could grow a session's memory without bound by joining and leaving over its 12 h lifetime. SRV-08's
10 joins/min/IP slows this down but does not bound it. The trade-off: such a join/leave loop can push out the
rejoin entries of legitimate viewers who are disconnected at that moment. Those viewers then get
`SESSION_NOT_FOUND` on rejoin and fall back to a code join (§9.2, §13 step 9), and the join loop shows up in
`viewer.count`.

Until SRV-15 implements rejoin, `viewer.join{sessionId, viewerToken}` answers `SESSION_NOT_FOUND`
(`retryable: false`, socket kept open). This is the documented trigger for the code fallback on the same
socket; web-viewer and quest-app need no special case.

## Notes / suspected cause

Suggestion for release: in architecture §3, say "kept until the session ends or, while disconnected, until
`3 × MAX_VIEWERS` newer entries exist".

## Related: more relay→client control messages without `sessionId` (T11)

Adds to `docs/testing/reports/2026-10-18-server-7.md`, which covers `session.publisherState`: `viewer.count` and
`scene.state` (protocol §5.3, §8.3) have no `sessionId` either, although architecture §8 T11 promises
"`sessionId` in every relay→client control message so clients drop mismatches". The relay sends exactly what the
schemas define. Its `viewer.count` fan-out iterates only the session's own publisher and viewers, and a
two-session test covers that. Suggestion as in server-7: an optional `sessionId` on these messages (additive,
1.x), or narrower T11 wording.
