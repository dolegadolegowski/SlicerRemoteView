# §2 "MUST reply `error` `UNSUPPORTED_TYPE`" contradicts §11 for clients

- **Reported by**: slicer (`ws/slicer`, SLC-06 review, commit `db3a42b`)
- **Affects**: protocol — `docs/protocol.md` §2 (Versioning), §11 (Permissions matrix); web, quest (viewers) read the
  same rule
- **Severity**: low (wording; no interoperability problem as long as clients stay silent)
- **Milestone**: M1
- **Protocol**: v1.0 §2, §11
- **Status**: open

## Steps to reproduce

1. Read §2: "A receiver MUST ignore unknown fields and MUST reply `error` `UNSUPPORTED_TYPE` (not close) to an unknown
   message type of a known major version."
2. Read §11: `pong`, `error` are sent only by the relay (`relay → publisher`, `relay → viewer`); a client sending
   `error` breaks the matrix and earns `error` `UNAUTHORIZED` and, the second time, close `1008`.

## Expected

One rule for clients that receive an unknown message type of the same major version.

## Actual

§2 read literally requires the publisher and the viewers to answer an unknown type with `error`, which §11 forbids.
The slicer client (`slicer-plugin/RemoteView/remoteview_core/protocol_client.py`, SLC-06) follows §11 and §14: it
ignores unknown types silently.

## Notes / suspected cause

Proposed wording for §2: "The **relay** MUST reply `error` `UNSUPPORTED_TYPE` (not close) to an unknown message type of
a known major version; clients ignore unknown message types (§11, §14)."
