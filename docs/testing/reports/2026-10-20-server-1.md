# §12 rate limits: what the relay does beyond the wording

- **Reported by**: server (`ws/server`, SRV-08 review)
- **Affects**: protocol — `docs/protocol.md` §12 (and §9.2 `RATE_LIMITED`); release — `docs/architecture.md` §8 T1/T3;
  qa — `tests/` harnesses (QA-02, QA-08): run the relay with `TRUST_PROXY=true` and give each simulated client its
  own `X-Forwarded-For` address, or the per-address limits refuse a load test from one host
- **Severity**: low
- **Milestone**: M1
- **Protocol**: v1.0 §12
- **Status**: triaged (PRO-20)

## Steps to reproduce

1. From one address, fail 20 `viewer.join{code}` within 10 minutes.
2. Wait one minute, then join again.
3. Separately, send upgrades or joins from many addresses of one IPv6 /64, or `session.create{preferredCode}`
   with free codes.

## Expected

§12 says "after 20 failed joins within 10 min the IP is banned for 10 min (`RATE_LIMITED`,
`details.retryAfterS: 600`)". It names limits per IP, and it does not mention `preferredCode`.

## Actual

The relay (SRV-08) differs in three ways. Each tightens or clarifies §12; none loosens it:

1. **`retryAfterS` during a ban is the time left**, i.e. 600 right after the ban starts and 540 a minute later.
   A client that waits `retryAfterS` gets through on its next attempt instead of being refused again.
2. **"Per IP" means per address bucket**: an IPv4 address, or an IPv6 /64, which is one subscriber's prefix and
   the default of `@fastify/rate-limit` (`ipv6Subnet: 64`). Otherwise one host could rotate through its own
   prefix for a fresh budget on every attempt. IPv4-mapped IPv6 counts as the IPv4 address.
3. **`session.create{preferredCode}` is a code probe.** Whether the code is granted shows whether it is free.
   So a well-formed `preferredCode` counts as a failed join of the address (not as a join attempt), granted or
   not. It is silently ignored (a fresh code is drawn) while the address is banned, and during the global alarm
   also above 3 per minute. It does not need a slot of the per-minute join
   window: otherwise viewers behind the presenter's NAT who retry the old code during a redeploy (§4.3) could cost
   the presenter the code on the screen (§13 step 9). With 5 creates/min the probe stays no faster than
   `viewer.join`, and the 20-failure ban bounds both together. A real publisher sends one after a relay restart.
   Trade-off: if several presenters share one NAT and their viewers produce 20 failed joins within 10 minutes,
   that address is banned and a redeployed presenter gets a fresh code. This closes report
   `2026-10-18-server-3.md`.

Two more details: upgrades refused for their `Origin` or subprotocol do not count toward the 30/min upgrade
limit (a foreign web page must not be able to lock out a shared NAT); a join with the right code that is
refused `SESSION_FULL` gives its attempt back, like a successful join.

## Notes / suspected cause

Suggested §12 wording: "`details.retryAfterS` = seconds until the ban ends (≤ 600)"; "per IP (an IPv6 /64
counts as one)"; "a well-formed `preferredCode` counts as a failed join (not as a join attempt) and is ignored
while the address is banned". For release, T1/T3 could
mention the /64 rule.
