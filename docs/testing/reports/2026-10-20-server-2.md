# `byteLength` above 64 MiB: the schema says INVALID_MESSAGE, §6.2 says PAYLOAD_TOO_LARGE

- **Reported by**: server (`ws/server`, SRV-09)
- **Affects**: protocol — `shared/schema/defs.schema.json` (`byteLength.maximum`), `docs/protocol.md` §6.2, §9.2
- **Severity**: low
- **Milestone**: M1
- **Protocol**: v1.0 §3.3, §6.2, §9.2, §14
- **Status**: open

## Steps to reproduce

1. Validate `scene.snapshot.begin{byteLength: 67108865, …}` with `parseEnvelope` from `shared`.

## Expected

§6.2: "The relay rejects the message with `error` `PAYLOAD_TOO_LARGE` if `byteLength > MAX_SNAPSHOT_BYTES`".
§9.2 lists `PAYLOAD_TOO_LARGE` for "snapshot … above limits", and the SRV-09 acceptance criterion expects it for
67,108,865 bytes.

## Actual

The `byteLength` definition has `"maximum": 67108864`, so a strict receiver answers `INVALID_MESSAGE` (a
protocol-violation strike) for anything above the protocol maximum. Only values between a lower configured
`MAX_SNAPSHOT_BYTES` and 64 MiB reach the `PAYLOAD_TOO_LARGE` rule.

The relay follows §6.2 (§14: "this document is normative for behaviour (… limits …)"). Before validation it
clamps an oversized `byteLength` of `scene.snapshot.begin` to the maximum, remembers that it did, and answers
`PAYLOAD_TOO_LARGE{maxSnapshotBytes}` (`relay-server/src/ws/snapshot.ts`).

## Related: `sceneVersion` has no upper bound in the schema

§6.3 carries `sceneVersion` in the chunk header as a uint32, and §8.4 says versions are uint32. The `sceneVersion`
and `snapshotVersion` defs only have `minimum`. A `begin` with `sceneVersion` 2^32 passes the schema, but no
chunk can ever name it. The relay answers `INVALID_MESSAGE{instancePath:"/sceneVersion"}` before the version
counts as used. Suggestion: `"maximum": 4294967295` on both defs.

## Notes / suspected cause

Suggestion for the protocol workstream: drop `maximum` from `byteLength` in the schema, and leave the 64 MiB cap
to §3.3/§6.2 and `PAYLOAD_TOO_LARGE`, so that every receiver gives the same answer. Alternatively, state in §6.2
that above the protocol maximum the answer is `INVALID_MESSAGE`. In that case the SRV-09 criterion has to change.
