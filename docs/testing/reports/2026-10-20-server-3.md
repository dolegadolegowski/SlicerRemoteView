# A viewer dropped from the stream mid-snapshot gets `ready` for that version, without an abort

- **Reported by**: server (`ws/server`, SRV-10)
- **Affects**: web — snapshot receiver (`web-viewer/`); quest — snapshot receiver (`quest-app/`); protocol — §6.4 wording
- **Severity**: low
- **Milestone**: M1
- **Protocol**: v1.0 §3.3 (watermarks), §6.3, §6.4 (a), §6.5
- **Status**: triaged (PRO-20; web/quest, 2026-10-27-protocol-3)

## Steps to reproduce

1. Two viewers join a session; the publisher sends `scene.snapshot.begin{sceneVersion: 4}` and some chunks.
2. Viewer B stops reading, so its relay-side `bufferedAmount` reaches the 4 MiB soft watermark before the next chunk.
3. The publisher sends the remaining chunks and `scene.snapshot.end`.

## Expected

§6.4 (a): viewers "skipped during streaming because their `bufferedAmount` exceeded the soft watermark" get
`scene.snapshot.ready` and fetch the version over HTTP (§6.5).

## Actual (relay behaviour, by design)

B received `begin{sceneVersion: 4}` and the first chunks, then no more chunks, no `end` and no
`scene.snapshot.abort` (none of the abort reasons fits), and after the publisher's `end` it gets
`scene.snapshot.ready{sceneVersion: 4, …}` (`relay-server/src/ws/fanout.ts`). A viewer whose `bufferedAmount` was
already at 4 MiB at `begin` gets no `begin` at all, only `ready`.

## Notes / suspected cause

The protocol does not spell out what a receiver does with a partial stream when `ready` arrives for the same
`sceneVersion`. Viewers should treat `scene.snapshot.ready` for the version they are assembling as "discard the
partial buffer and fetch over HTTP" (and ignore any late chunk of that version). Suggestion for the protocol
workstream: add one sentence to §6.4 (a), and a test in the web/quest receivers for begin → chunks → `ready` of
the same version.
