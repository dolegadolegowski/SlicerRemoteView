# Viewer token hashes of an ended session are kept for `CODE_QUARANTINE_S` (for `410`)

- **Reported by**: server (`ws/server`, SRV-11)
- **Affects**: release — `docs/architecture.md` §2.9 (session end) and §3 (registry data model); protocol —
  `docs/protocol.md` §10 wording; web, quest — HTTP scene download (see the last section)
- **Severity**: low
- **Milestone**: M1
- **Protocol**: v1.0 §10 (`GET /api/scene/:sceneVersion`: "`410` session gone")
- **Status**: open

## Steps to reproduce

1. A viewer joins a session and gets its `viewerToken`.
2. The publisher sends `session.close` (or the session expires).
3. The viewer calls `GET /api/scene/1` with `Authorization: Bearer <viewerToken>`.

## Expected

Protocol §10 answers `410` for a session that is gone and `401` for an unknown token. To tell the two apart after
the session is released, the relay must recognise the token of a session that ended.

## Actual (relay behaviour, by design)

The relay keeps the SHA-256 hashes of an ended session's viewer tokens for `CODE_QUARANTINE_S` (default 600 s),
at most `MAX_SESSIONS` × 3 × `MAX_VIEWERS` of them (oldest out). They are used only to answer `410` and grant no
access; after that window the same token answers `401` (`relay-server/src/registry.ts`, `tokenEnded`).

Architecture §2.9 says the relay "forgets token hashes" when a session ends, and the §3 registry model has no
such set.

## Notes / suggested change

For `release`: in §2.9 say that ended viewer-token hashes are kept for `CODE_QUARANTINE_S` (bounded) only to answer
`410`, and add the set to the §3 registry model. Tokens themselves are never stored (NFR-17), only hashes.

## Related: §10 says "`401` unknown/expired token"

Viewer tokens have no expiry of their own (§5.2: the token dies with the session), so "expired token" can be read
as "token of an expired session" — which the relay answers with `410` for `CODE_QUARANTINE_S`, then `401`. WEB-06
maps `401` to the code-entry screen and `410` to "session ended", so the two readings lead to different screens.
Suggested §10 wording for the protocol workstream: "`401` unknown token, or one the relay no longer remembers
(more than `CODE_QUARANTINE_S` after its session ended); `410` the token's session was closed or expired".

## Related: the relay can cut a scene download mid-body (web, quest)

`GET /api/scene/:v` is ended by the relay when the `Buffer` it sends leaves the cache — the session ends or a newer
snapshot replaces it — and after 60 s without progress (`relay-server/src/http/scene.ts`). The client then sees a
body shorter than `Content-Length` or a connection reset. Viewers already verify the sha256 (§6.4); they should treat
a cut download like a failed one: drop the partial bytes and, if the session is still live, fetch the version the
latest `scene.snapshot.ready` (or `viewer.joined`) announced.
