# After a relay restart, a lecture room behind one NAT address can trip the per-IP join ban while rejoining by code

- **Reported by**: web (`ws/web`, WEB-14)
- **Affects**: server — `viewer.join` rate limiting and ban (SRV-08/SRV-15, `relay-server/`); release — protocol §12
  wording, NFR-20; qa — the NAT-classroom scenario of ADR 0008 (`docs/security.md`)
- **Severity**: medium (NFR-20 recovery can turn into a 10-minute lock-out for a whole room; no data exposure)
- **Milestone**: M2
- **Protocol**: v1.0 §9.2 (`SESSION_NOT_FOUND`), §12 (per-IP limits, ban), §13 step 9
- **Status**: open

## Steps to reproduce

(Analysis of the documented rules; the relay does not implement viewer rejoin yet — SRV-15 is `todo`.)

1. 20 viewers (`MAX_VIEWERS`) on one lecture-hall Wi-Fi share one public IP (ADR 0008 "Classroom NAT").
2. The relay is redeployed: every socket gets `4008`, the new instance has an empty registry (§13 step 9).
3. Each viewer rejoins with its token → `SESSION_NOT_FOUND`, then joins by the code. The presenter re-creates the
   session 0–3 s after the restart; until then every code join is `INVALID_CODE`, a failed join for the room's IP.

## Expected

NFR-20: "viewers rejoin without user action" within 60 s of the relay being healthy. ADR 0008: the per-IP join
limit "must not block legitimate joins" behind a classroom NAT.

## Actual

§12 bans the IP for 10 min after **20 failed joins within 10 min**. The registry is empty right after a restart, so
the room's first code joins fail until the presenter is back; 20 viewers × one early attempt is already 20. If the
presenter does not come back (Slicer closed), every scheduled attempt fails and the ban also blocks the room from
joining the presenter's next session by its new code for 10 min. The 10/min per-IP limit on code joins also delays
a 20-viewer room by up to two minutes after a restart (rejoins with a token bypass it, but tokens die with the
restart). The WebSocket upgrade limit (30/min per IP) is also exceeded when each of 20 viewers needs two sockets
(token join, then code join).

## What the web viewer does (WEB-14)

To keep failures low it does not retry the code at once and on every backoff step: the first code join waits 4 s
(+ 0–2 s jitter) after `SESSION_NOT_FOUND`, giving the presenter its head start, and `INVALID_CODE` is retried only at
≈ 15, 35 and 60 s (4 attempts, then "Session not found" on the code entry). That is at most 4 failures per viewer
(≤ 1 in the usual case). The code join uses a new socket. §9.2 keeps the old one open 10 s "for fallback", but neither §5 nor
SRV-15 says that a viewer may send a second `viewer.join` there, and the relay's dispatcher comment
(`relay-server/src/ws/dispatch.ts` on `ws/server`, rule 5) reads as answering anything but `ping` on a socket not yet
bound to a session with `UNAUTHORIZED` (second offence `1008`, which a viewer must not retry). A new socket is valid
either way; it costs one more WebSocket upgrade per viewer `[TODO verify]` against SRV-15.

## Notes / suspected cause

Suggested (server/release decision): do not count `INVALID_CODE` towards the ban for a few minutes after the relay
starts (`RESTART_GRACE_S`), or count failures per (IP, code) for codes that were live before the restart; state in
§9.2 whether a viewer may send its code `viewer.join` on the socket that got `SESSION_NOT_FOUND`; let QA cover the
"20 viewers, one IP, relay restart" scenario (ADR 0008 follow-up).
