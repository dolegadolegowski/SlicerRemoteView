# FR-09 says "16-bit positions/normals"; protocol §7.4 and the writer store normals as 8-bit `BYTE`

- **Reported by**: slicer (`ws/slicer`, SLC-12, on top of `51b166c`)
- **Affects**: release — `docs/requirements.md` FR-09 (and the size note `[TODO verify]` in `docs/architecture.md` §4,
  "1 M quantized triangles ≈ 20–30 MiB")
- **Severity**: low
- **Milestone**: M2
- **Protocol**: none (§7.2 and §7.4 already allow what the writer does)
- **Status**: open

## Steps to reproduce

1. `write_glb([...], RootExtras(...), quantize=True)` (`slicer-plugin/RemoteView/remoteview_core/glb_writer.py`) — what
   every snapshot now uses (`snapshot.build_snapshot`, SLC-12).
2. Read the `NORMAL` accessor of the GLB.

## Expected

FR-09: "The GLB uses `KHR_mesh_quantization` (16-bit positions/normals) …".

## Actual

`POSITION` is 16-bit (`SHORT`, non-normalised); `NORMAL` is normalised 8-bit `BYTE` padded to a 4-byte stride, as
protocol §7.4 allows ("stored as `FLOAT` or normalised `BYTE`") and `docs/architecture.md` §6 proposes. The angle error
is under half a degree (`tests/test_glb_quantize.py`); a 16-bit normal (`SHORT`, 8 bytes a vertex with padding) would
cost 4 more bytes a vertex for no visible gain.

## Notes / suspected cause

Please align FR-09 with §7.4: "16-bit positions, 8-bit (or 16-bit) normals". For the `[TODO verify]` in architecture
§4: measured with the writer, a `vtkSphereSource` of 99,456 triangles and 49,730 vertices is 1.19 MB quantised (12 bytes
a vertex, uint16 indices), so the `quest3` budget of 1 M triangles in ten such nodes is about 11.9 MB — well under the
20–30 MiB of the note; with uint32 indices (a node above 65,535 vertices — the 100k-per-node cap keeps nodes below it
for closed meshes) it would be about 18 MB. Research note: `docs/research/slicer-quantize.md`.
