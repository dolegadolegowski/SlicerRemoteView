# The relay serves only `/`, `/j` and `/assets/*`: the viewer's manifest and icons 404, and its CSP refuses `fetch(blob:)`

- **Reported by**: web (`ws/web`, WEB-17 review and WEB-19)
- **Affects**: server — static viewer hosting and headers (SRV-16, `relay-server/src/http/static.ts`, `app.ts`)
- **Severity**: medium (Add to Home Screen gets no icon or manifest on the deployed relay; no data exposure)
- **Milestone**: M2 (manifest, icons), M3a (CSP note)
- **Protocol**: v1.0 §10 (HTTP endpoints), ADR 0006 §4 (CSP)
- **Status**: open

## 1. `/manifest.webmanifest` and `/icons/*` are not served

### Steps to reproduce

(Code reading on `origin/ws/server`, 2026-10-21; the viewer build is not deployed behind the relay yet.)

1. Build the viewer (`npm run build -w web-viewer`): `dist/` holds `index.html`, `assets/`, `manifest.webmanifest`
   and `icons/{icon-192.png, icon-512.png, apple-touch-icon.png}` (WEB-17, from `web-viewer/public/`).
2. Serve it with the relay (`relay-server/public/` = the viewer's `dist/`, SRV-20).
3. Request `GET /manifest.webmanifest` and `GET /icons/apple-touch-icon.png`.

### Expected

`200` with `application/manifest+json` (or `application/json`) and `image/png`. `index.html` links these exact paths
(`<link rel="manifest" href="/manifest.webmanifest">`, `rel="icon"`, `rel="apple-touch-icon"`), and the manifest names
the icons by these paths. Chrome needs the manifest and its 192/512 px icons to offer installation (NFR-26); iOS uses
`apple-touch-icon` for the Home Screen icon (NFR-25). These files are not hashed, so `no-cache` or a short `max-age`
fits them, not `immutable`.

### Actual

`registerStatic` registers `@fastify/static` for `assets/` only (`prefix: "/assets/"`, `wildcard: false`) plus `/`
and `/j`; every other path is `404 {"error":"NOT_FOUND"}`. Installing the viewer from the deployed relay therefore
gets no manifest (Chrome: no install, or a generic one) and no icon (iOS: a screenshot of the page).

### Proposal

Register the few root files of the build explicitly — `manifest.webmanifest` and `icons/*.png`, found at start like
the assets (still no catch-all, so `/<CODE>` keeps failing) — with `Cache-Control: no-cache` and the content types
above. `@fastify/static`'s MIME table may not know `.webmanifest` (`[TODO verify]`); set it explicitly if not. The
web e2e `e2e/pwa.spec.ts` asserts the paths and content types against `vite preview`; a relay test could reuse
`web-viewer/dist` the way SRV-16 criterion 3 does.

The WebXR input profiles (WEB-19) avoid this: they are built into `dist/assets/xr-profiles-<version>/`, where the
relay already serves them, and the version in the path keeps the 30-day `immutable` cache correct.

## 2. `connect-src 'self' wss:` refuses three.js' `fetch(blob:…)` for GLB textures

three.js' `GLTFLoader` turns images embedded in a GLB into `blob:` URLs and, wherever `createImageBitmap` exists
(Chromium, so Meta Quest Browser), reads them with `ImageBitmapLoader`, i.e. `fetch(blob:…)`; a refused image leaves
the model untextured and logs "Couldn't load texture" (`docs/research/web-xr.md` §1). The relay's CSP has no `blob:` in
`connect-src`, so the Quest controller models (textured GLBs) would show grey, with console errors.
`docs/plan/server.md` already names this as ADR 0006's "revisit CSP" follow-up.

The web viewer does not need a change: its XR module loads those GLBs with a GLTFLoader plugin that switches the
texture loader to `TextureLoader` (`<img src=blob:…>`, allowed by `img-src 'self' data: blob:`), and
`web-viewer/e2e/xr.spec.ts` runs the WebXR session under the relay's CSP to prove it. The snapshot GLBs carry no
images (§7.1). Recorded so that a future CSP change neither breaks this (keep `img-src blob:`) nor is made for it
(`connect-src blob:` is not needed by the viewer).
