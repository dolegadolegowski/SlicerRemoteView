# Incremental updates: relay rules the protocol does not state yet

- **Reported by**: server (`ws/server`, SRV-12)
- **Affects**: protocol — `docs/protocol.md` §3.3, §6.2, §8.1, §8.4, §9.2, §9.3; slicer — change senders and
  resume (`slicer-plugin/`, plan SLC-16, SLC-17; `remoteview_core/protocol_client.py` `SceneVersionCounter`)
- **Severity**: medium
- **Milestone**: M2
- **Protocol**: v1.0 §3.3, §6.2, §8.1–§8.4, §9.2, §9.3
- **Status**: triaged (PRO-20)

## Steps to reproduce

1. A publisher sends `scene.update` messages that together name more than 1,000 distinct node ids since the
   last snapshot, e.g. 1,500 appearance changes split into two updates as SLC-16 criterion 3 does.
2. A publisher sends `scene.nodeAdded` between `scene.snapshot.begin` and `scene.snapshot.end`.
3. A publisher's uplink drops while its `scene.snapshot.begin{sceneVersion:5}` is in flight (the relay aborts
   it, `PUBLISHER_GONE`; the last accepted version is 1); it resumes and continues from
   `session.resumed.sceneVersion`, as §8.4 says (before SRV-15 that would have been 1).
4. A publisher sends `scene.update{baseVersion:0, sceneVersion:1}` before its first snapshot.
5. A viewer that reads nothing keeps receiving updates until its send buffer nears 8 MiB.

## Expected (protocol v1.0)

1. §3.3 only says that "larger updates MUST be split"; it sets no limit on the state the relay merges.
2. §6.2 and §8.1 refuse only `scene.update` and `scene.nodeRemoved` while a snapshot is in flight.
3. §8.4: "After `session.resume` the publisher continues from `session.resumed.sceneVersion`".
4. Nothing: §8.4 starts the versions "at 1 for the first snapshot" but does not say updates must follow it.
5. §9.2: `SLOW_CONSUMER` for a `bufferedAmount` "over the hard watermark (8 MiB)".

## Actual (relay behaviour, by design — `relay-server/src/ws/state.ts`, SRV-12)

1. The merged state (`nodeState`, sent to late joiners as `scene.state`) holds at most 1,000 node ids
   (`MAX_STATE_NODES` = `maxChanges`, the bound architecture §5 assumes: "≤ 1,000 nodes × ~300 B"). An update
   or `scene.nodeRemoved` that would take it beyond is refused with `error
   BAD_SEQUENCE{details.field:"nodeState"}` (retryable) and not forwarded; the publisher's next snapshot
   empties the state. Without the cap a publisher could grow relay memory without bound with ids that are in
   no GLB (T3). `BAD_SEQUENCE` was chosen because its documented reaction (§8.1: "the publisher then re-syncs
   by sending a snapshot") is the recovery needed; `CAPACITY` (relay-wide, `4006`) and `PAYLOAD_TOO_LARGE`
   (not retryable) would mislead. The 1,500-node case of SLC-16 criterion 3 therefore gets its second update
   refused when all ids are distinct — far beyond every profile's "Max visible nodes" (§7.5: 60–120), but the
   publisher must then send a snapshot, and SLC-16/SLC-17 have no step for a refused update today.
2. `scene.nodeAdded` too is refused while a snapshot is in flight (`BAD_SEQUENCE{field:"snapshotInFlight"}`,
   retryable; the server plan's SRV-12 text says "any of the three"). It is needed for the versions: a
   `scene.nodeAdded{baseVersion:1, sceneVersion:3}` accepted during `begin{2}` would let `end{2}` move the
   session's version back from 3 to 2. SLC-16 queues only `scene.update`/`scene.nodeRemoved`.
3. The relay keeps §8.4's "strictly increasing across snapshots and updates" over every version a `begin`
   announced, accepted, refused or aborted (SRV-09 for `begin`, SRV-12 for updates). The resumed publisher's
   versions 2–5 are refused: updates with `BAD_SEQUENCE{field:"sceneVersion"}`, the re-sync `begin`s with
   `BAD_SEQUENCE` too, and the snapshot path counts those as strikes towards `4007` (third one closes). Not
   reachable before SRV-15, but `SceneVersionCounter.continue_from()` sets `_last = version` and can lower the
   counter, against its own docstring ("a version is never reused, even when the relay rejected it").
   **Since SRV-15** the relay answers `session.resumed.sceneVersion` = the highest version used, accepted or
   not — max(last accepted, highest `begin` announced) —, so a publisher that continues from it as §8.4 says
   never re-announces a used version: in step 3 it gets `sceneVersion: 5, snapshotVersion: 1`. The value differs
   from the last accepted version (the one `baseVersion` is checked against) only after a `begin` that was not
   accepted announced a version above the last accepted one, until a higher version is accepted; the publisher
   then holds a scene newer than
   `snapshotVersion` and MUST send a snapshot (§4.3) — its next `begin{6}` is accepted; an update first would get
   `BAD_SEQUENCE{field:"baseVersion"}` and the §8.1 re-sync.
4. An update before the session's first snapshot is refused with `BAD_SEQUENCE{field:"noSnapshot"}`: §8.4
   starts the versions with a snapshot, a viewer applies updates to a GLB (§8.3), and `scene.state` would
   otherwise list nodes with `snapshotVersion: null`, which §8.3 does not describe.
5. An update that would take a viewer's send buffer above the 8 MiB hard watermark closes that viewer
   (`SLOW_CONSUMER`, `4010`) before the send, not after: unlike a snapshot chunk, an update cannot be deferred
   (the viewer re-syncs on reconnect with `scene.snapshot.ready` and `scene.state`). §9.2 says "over the hard
   watermark".

The `details.field` values of these refusals are `snapshotInFlight`, `noSnapshot`, `baseVersion`,
`sceneVersion` and `nodeState`. The update path's `BAD_SEQUENCE` answers close nothing and count no strike
(§9.2's table: "none"); the snapshot path's count towards `4007` (§9.3: "repeated
`INVALID_MESSAGE`/`BAD_SEQUENCE`").

## Notes / suggested change

- Protocol, §3.3: a row "Merged update state since the last snapshot | 1,000 node ids | relay (`BAD_SEQUENCE`
  `{field:"nodeState"}`) | bounds `scene.state` (≈ 250 KiB typical, ≈ 0.65 MiB worst case) and relay memory;
  the publisher sends a snapshot".
- Protocol, §6.2/§8.1: name `scene.nodeAdded` next to `scene.update` and `scene.nodeRemoved` in the in-flight
  rule; say that updates follow the first snapshot; list the `details.field` values above under `BAD_SEQUENCE`
  in §9.2.
- Protocol, §3.3/§9.2: "an update that would take a viewer above the hard watermark closes it instead".
- Protocol, §9.2/§9.3: say which `BAD_SEQUENCE`s count towards `4007` (the relay: the snapshot path's — a
  chunk stream out of order — but not the update path's, which are benign races over a long session and answer
  one message each).
- Protocol, §8.4 — one of two wordings: (a) what the relay does since SRV-15: "`session.resumed.sceneVersion`
  is the highest version used in the session, accepted or not; after a resume the publisher continues above
  it, and sends a snapshot when `sceneVersion` is not the last version it sent or `snapshotVersion` is not its
  last snapshot" (§4.3's "older than the publisher's current scene" read literally would force a re-upload
  after every resume that follows an update, against §13 step 10); or (b) "the relay answers
  the last accepted version, and the publisher continues **above the highest version it has used** (at least
  `session.resumed.sceneVersion`)" — then the relay goes back to the last accepted version. Either way, Slicer:
  `continue_from(v)` → `_last = max(_last, v)`, which is safe under both.
- Slicer, SLC-16: queue `scene.nodeAdded` too while a snapshot is in flight; on `BAD_SEQUENCE` for an update
  (`baseVersion`, `sceneVersion`, `nodeState`) re-sync with a snapshot (§8.1); `noSnapshot` → send the first
  snapshot; `snapshotInFlight` keeps the queue-and-resend rule.
