# load-smoke test (SRV-21) depends on loopback socket buffering: fails on macOS

- **Reported by**: release (`main`, at 5f6b439)
- **Affects**: server — `relay-server/test/load-smoke.test.ts`, `relay-server/scripts/load-smoke.ts`
- **Severity**: low (test only; the relay itself behaves as designed)
- **Milestone**: M2
- **Status**: open

## What happens

On macOS 27 (Apple Silicon, Node 22) `npm test -w relay-server -- load-smoke` fails in both tests, alone and
after a fresh `npm run build -w shared -w relay-server`; the rest of the relay suite passes (1051 tests).

1. *a small run passes every check*: `result.failures` is `["cycle 1: streamed 1, deferred 2, not all 3 streamed"]`
   — the first cycle defers two viewers that the test expects to be streamed.
2. *a run that times out still takes the relay down*: the promise resolves instead of rejecting, with
   `failures: ["the stopped viewer was not deferred in 30 cycles"]`; every cycle reports `viewersStreamed: 3,
   viewersDeferred: 0, fanoutMs: 1–2`.

Both point at the loopback transport rather than the relay: on macOS the loopback TCP send/receive buffers are
large enough that a viewer which stops reading never raises `bufferedAmount` above the high watermark within the
run, so the deferral the test waits for never happens; on Linux (the sandbox where SRV-21 was developed and the CI
runner) the buffers are small enough that the stopped viewer is deferred within a few cycles.

## Please consider

- Make the stopped-viewer check independent of kernel buffering, e.g. by sending enough bytes per cycle to exceed
  the watermark regardless of the socket buffer (the snapshot in the test is 3,400 B), or by driving the deferral
  through the relay's own watermark rather than TCP back-pressure.
- Until then mark the two tests as Linux-only (`describe.skipIf(process.platform !== "linux")`) with this report as
  the reason, so that a macOS developer's `npm test` stays green while CI (DEP-01, Linux) keeps the check.
