# `scene.request`: the relay's 5 s throttle and other answers the protocol does not state yet

- **Reported by**: server (`ws/server`, SRV-13)
- **Affects**: protocol — `docs/protocol.md` §8.3, §6.5, §13 step 7; web —
  `web-viewer/src/protocol/scene-versions.ts` `gap()` and `scene-loader.ts` `requestResync`/`resyncOnce`;
  quest — QST-04/QST-13 (gap → `scene.request`, not built yet); release — `docs/architecture.md` §3
  (`sceneRequests: number`) and §2.3 (fan-out diagram, deferred viewer B)
- **Severity**: medium (a silent desync until the next snapshot; unlikely)
- **Milestone**: M2
- **Protocol**: v1.0 §8.3, §6.5, §9.2
- **Status**: triaged (PRO-20; web/quest, 2026-10-27-protocol-3)

## Steps to reproduce

1. A web viewer gets an answer to a `scene.request`, then within 5 s sees another version gap (a live update
   whose `baseVersion` is not its version, `scene-versions.ts` `gap()`) and sends a second request.
2. A viewer is deferred at a snapshot's `end` (it gets `scene.snapshot.ready`).
3. A viewer that cannot use HTTP relies on §6.5's streamed copy.

## Expected (protocol v1.0)

1. §8.3: "The relay answers with `scene.snapshot.ready` if `haveSnapshotVersion` differs from its cached
   snapshot, then `scene.state`" — every request is answered.
2. §8.3: `scene.state` is sent "(b) after `scene.snapshot.ready`", but §13 step 7 shows the deferred viewer B
   getting only `scene.snapshot.ready{sceneVersion:4}`.
3. §6.5: a viewer "will get a streamed copy only if the relay has spare budget".

## Actual (relay behaviour, by design — `relay-server/src/ws/viewer.ts`, `ws/fanout.ts`, SRV-13)

1. One request per viewer entry is answered per 5 s (plan SRV-13 criterion 3, architecture §3), counted from
   the last answered one; the others get nothing — no reply, no error, no strike. `RATE_LIMITED` is not used:
   §9.2 defines it for join and create attempts and pairs it with `4006`. The web viewer has no timeout for
   its request: `awaitingState` stays true, and live updates queue (256, then dropped) until a later
   `scene.state`, a shown snapshot or a rejoin.
2. An empty `scene.state{sceneVersion = snapshotVersion = N, nodes: [], removed: []}` follows every
   `scene.snapshot.ready` sent at an accepted `end`, without `replyTo`; a streamed viewer gets `end` only.
3. The relay never streams a copy: it always answers with `scene.snapshot.ready` (HTTP).
4. A `haveSnapshotVersion` equal to the cached snapshot gets no `ready`, whatever the `reason`: a client that
   reports a version whose hash failed as "have" is not told to fetch it again. The web viewer reports the
   last version that loaded, so it is not affected.
5. The relay keeps the time of each viewer entry's last answer, not architecture §3's `sceneRequests: number`.

## Notes / suggested change

- Protocol, §8.3: "The relay answers at most one `scene.request` per viewer every 5 s and ignores the others
  without an error; a viewer that gets no `scene.state` within 5 s sends its request again." Define
  `haveSnapshotVersion` as the last snapshot version whose bytes the viewer verified.
- Protocol, §6.5: drop the streamed-copy sentence, or mark it as not implemented in v1.
- Web and Quest: re-send an unanswered request after 5 s, once per gap.
- Release: §13 step 7 and architecture §2.3 should show the empty `scene.state` after the deferred viewer's
  `scene.snapshot.ready`; architecture §3 the per-viewer time instead of a counter.
