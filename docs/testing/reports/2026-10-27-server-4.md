# Resume and rejoin: answers the protocol does not state yet (SRV-15)

- **Reported by**: server (`ws/server`, SRV-15)
- **Affects**: protocol — `docs/protocol.md` §4.3, §4.4, §4.6, §5.1, §9.2, §11; web — WEB-14 (fallback after
  `SESSION_NOT_FOUND`, answers the `[TODO verify]` of report `2026-10-20-web-2.md`); slicer — SLC-17 (resume);
  release — SRV-28 (ban exemption after a restart)
- **Severity**: low (no wire change for a compliant client; clarifications)
- **Milestone**: M2
- **Protocol**: v1.0 §4.3, §4.4, §4.6, §5.1, §9.2, §11
- **Status**: triaged (PRO-25: wording sync round 2, not yet in protocol.md); item 4's ban question decided — the user
  accepted the default, done in SRV-28

## Steps to reproduce

1. A publisher's grace ends (`graceEndsAt`) and it resumes a few seconds later, before the relay's next sweep.
2. A client sends a second `session.resume` (or a second token `viewer.join`) on the socket that got
   `SESSION_NOT_FOUND`.
3. A publisher whose old socket is still open (half-open) resumes on a new socket.
4. A viewer that got `SESSION_NOT_FOUND` for its token rejoin sends `viewer.join{code}` on the same socket.
5. A publisher with no viewers drops less than 60 s before its idle expiry and resumes within grace.

## Expected (protocol v1.0)

1. §4.3: resume is "allowed while the session is in `grace` (publisher offline ≤ `PUBLISHER_GRACE_S`)".
2. §11: "a second offence" closes `1008`; §4.3 says only that the publisher "can fall back to `session.create`".
3. §4.6: `session.publisherState` is "sent when the publisher disconnects (grace starts) and when it resumes".
4. §9.2's table: `SESSION_NOT_FOUND` — "socket kept open 10 s for fallback"; §12: "every failed
   `viewer.join` closes its socket".
5. §4.4: `session.expiring` 60 s before an idle expiry.

## Actual (relay behaviour, by design — `relay-server/src/ws/publisher.ts`, `ws/viewer.ts`, SRV-15)

1. A session whose grace ran out stays resumable until the sweep releases it (every 10 s): at most 10 s past
   `graceEndsAt`, so the code on the screen survives a resume that is a few seconds late.
2. One `session.resume` or token `viewer.join` per socket; the second gets `error UNAUTHORIZED` + `1008` at
   once (no first `UNAUTHORIZED` strike). After `SESSION_NOT_FOUND` the socket accepts only the fallback:
   `session.create` for a publisher, `viewer.join{code}` for a viewer.
3. After a half-open resume the viewers get no `session.publisherState` at all: they never got `online:false`.
   The old socket is closed `4011` and its snapshot in flight aborted `PUBLISHER_GONE`.
4. The code join on the `SESSION_NOT_FOUND` socket is accepted within a fresh 10 s window (from the error, not
   from the upgrade), with the usual per-address rate limit and ban. WEB-14 can use it and save one upgrade
   per viewer. Since SRV-28, for 120 s after the relay starts failed code joins do not count towards the ban
   (the 10/min limit and the global alarm still apply) — protocol §12 could say so: "for `RESTART_GRACE_S`
   (120 s) after a relay start, failed joins count towards the global alarm but not the per-IP ban".
5. An outstanding idle warning (no viewer since, not renewed) is repeated right after `session.resumed`:
   `session.expiring{reason:"IDLE", closesAt}` with the same `closesAt` — also when the old socket got it.
6. A token rejoin counts towards no join limit or ban, valid or not (one per socket; each costs an upgrade,
   30 a minute per address): the 256-bit token is not guessable, and a rejoin answers no question about codes.

## Notes / suggested change

- Protocol §4.3: "Allowed while the session is in `grace` — the relay may accept a resume until it releases
  the session, shortly after `graceEndsAt` — or while the old publisher socket is still open …"; "one
  `session.resume` per socket: a second one is `UNAUTHORIZED` + `1008`; only `session.create` may follow
  `SESSION_NOT_FOUND`". The same for a token rejoin in §5.1 (only a code join may follow).
- Protocol §4.6: "sent when grace starts and when a resume ends it".
- Protocol §9.2's table: "socket kept open 10 s from the error for the fallback (`session.create`, or a
  `viewer.join` with the code)", and §12: "… closes its socket, except that a code join may follow a token
  rejoin's `SESSION_NOT_FOUND`".
- Protocol §4.4: "an outstanding warning is repeated after `session.resumed`, with the same `closesAt`; a
  client treats a repeat with the same `closesAt` as the same warning".
- Protocol §12: "token rejoins, valid or not, count towards no join limit or ban; one per socket".
- Web (WEB-14): after `SESSION_NOT_FOUND` the code join may be sent on the same socket within 10 s.
