# A draining relay: the `503` answers the protocol does not list (SRV-17)

- **Reported by**: server (`ws/server`, SRV-17)
- **Affects**: protocol — `docs/protocol.md` §3.1 (upgrade refusals), §10 (`/healthz`); clients (web, slicer,
  quest) — an upgrade refused `503` during a redeploy
- **Severity**: low (additive; clients already retry a failed connection)
- **Milestone**: M2
- **Protocol**: v1.0 §3.1, §9.3 (`4008`), §10
- **Status**: triaged (PRO-25: wording sync round 2, not yet in protocol.md)

## Steps to reproduce

1. Send `SIGTERM` to the relay (a Railway redeploy) while a client opens a new WebSocket to it.
2. Request `GET /healthz` from the draining relay.

## Expected (protocol v1.0)

§3.1 lists no answer for an upgrade to a relay that is shutting down; §10 shows `/healthz` only as
`{ "status": "ok", … }`. Architecture §5/§9 say "stop accepting upgrades" and "`/healthz` returns `503` once
SIGTERM is received".

## Actual (relay behaviour, by design — `relay-server/src/app.ts` `drain()`, `ws/endpoint.ts`, SRV-17)

1. While draining, an upgrade that passes the Origin check gets HTTP `503 {"error":"RELAY_RESTARTING"}`,
   before the per-address limit (it spends none of the 30 a minute). Sockets already open get close `4008`
   with no message before it (§9.3).
2. `/healthz` answers `503 {"status":"draining","uptimeS":…,"sessions":…,"version":…}`.
3. A socket that does not complete its close within `min(5 s, RAILWAY_DEPLOYMENT_DRAINING_SECONDS − 1 s)` is
   cut: it sees `4008` only if the close frame already left the relay's send buffer, else `1006`.

## Notes / suggested change

- Protocol §3.1: "A relay that is draining for a restart answers the upgrade `503`
  `{"error":"RELAY_RESTARTING"}`; retry with the `4008` jitter (0–3 s) — the next attempt reaches the new
  instance."
- Protocol §10, `/healthz` row: "`503` with `status: "draining"` once the relay received SIGTERM".
- Clients: treat an upgrade answered `503` like close `4008` (reconnect after 0–3 s), and a `1006` right after a
  redeploy like any dropped connection. The Slicer transport already retries an HTTP `503`
  (`slicer-plugin/tests/test_transport.py`, `ws/slicer`).
