# `RELAY_TEST_FAST_TIMERS`: which timers should it shorten? (SRV-21)

- **Reported by**: server (`ws/server`, SRV-21)
- **Affects**: qa — QA-02 (stack harness: "`RELAY_TEST_FAST_TIMERS` where needed"), QA-05 ("20 failures in
  10 min (fast timers) → ban"); release — `docs/architecture.md` §9 ("shortens TTL/heartbeat timers for
  integration tests"); deploy — DEP-05 and DEP-13 (excluded from the env parity checks)
- **Severity**: low (test tooling; no production behaviour)
- **Milestone**: M2
- **Protocol**: none
- **Status**: open

## Steps to reproduce

1. Start the relay with `NODE_ENV=test RELAY_TEST_FAST_TIMERS=1`.
2. Run QA-05's ban case (20 failed joins from one address within 10 minutes).

## Expected

Architecture §9: the flag "shortens TTL/heartbeat timers for integration tests". QA-05 expects the 10-minute ban
window to be reachable in a test run.

## Actual (relay behaviour — `relay-server/src/config.ts`, SRV-02/SRV-21)

1. The flag is parsed (`config.testFastTimers`, honoured only under `NODE_ENV=test`) but shortens nothing yet.
2. The session timers it would most obviously shorten are already configurable down to 1 s:
   `SESSION_TTL_S`, `PUBLISHER_GRACE_S`, `SESSION_MAX_LIFETIME_S` (and `CODE_QUARANTINE_S` down to its floor).
3. Not configurable: the per-address windows (upgrades and joins per minute, the 10-minute failure window and
   ban, the one-hour global alarm, `src/ratelimit.ts`) and the limiter sweep (60 s), the heartbeat (30 s tick), the
   handshake (10 s), the registry sweep (10 s), the `session.expiring` lead (60 s — with `SESSION_TTL_S` below it the
   warning comes at the first sweep), the chunk inter-arrival timeout (120 s, §3.3), the `GET /api/scene` window (30 a minute
   per token) and download stall (60 s), the slow-consumer rules ("stuck" 60 s, terminate after 5 s), the publisher
   pause (≤ 5 s), the close timers (5 s to complete, ≤ 30 s to drain) and the scene-request throttle (5 s).
4. The load smoke (SRV-21) does not need the flag: none of its checks waits for a timer, and a shorter heartbeat
   would close its stopped viewer (`4009`) before the relay defers it.

## Notes / suggested change

- QA and release, please pick the set. Proposed default: `RELAY_TEST_FAST_TIMERS=1` divides the per-address
  windows and the ban by 60 (a minute becomes a second, the 10-minute ban 10 s) and the registry sweep to 1 s, with
  the limit counts unchanged (QA-05's "20 failures → ban" holds); heartbeat, handshake and slow-consumer timers keep
  their values (tests that need them use the manual clock in process). It stays behind `NODE_ENV=test` and out of
  `.env.example` (as now).
- What it weakens (T1): the same counts in windows 60 times shorter allow 60 times the guess rate — 10 joins a
  second per address, about 36,000 an hour. With architecture §8's arithmetic (join rate only, `S` = 100 sessions
  in 31^5 codes) that is about 0.13 expected hits per address-hour instead of the 0.2 % of the T1 row, if the flag
  ever reached production. Hence the guards below.
- A second guard, independent of `NODE_ENV`: QA-02 runs the shipped build with the flag, so the code path is in the
  image, and a Railway service variable overrides the image's `NODE_ENV=production`. Proposed: `loadConfig` throws a
  `ConfigError` naming `RELAY_TEST_FAST_TIMERS` when the flag is on and a Railway-injected variable is set
  (`RAILWAY_PUBLIC_DOMAIN`, already read by the relay; others `[TODO verify]`), and the `relay starting` line carries
  `testFastTimers` and a `warn` line follows when it is on, so DEP-06's checklist can confirm it is `false`.
- Deploy (DEP-05, DEP-13): the parity checks list the flag as ignored, so it would pass silently if it appeared in
  `.railway/railway.ts`. Proposed: a deny entry — fail when `RELAY_TEST_FAST_TIMERS`, or a `NODE_ENV` other than
  `production`, is set there.
- The global alarm (more than 1,000 failed joins in an hour → 3 joins a minute per address for an hour,
  `src/ratelimit.ts`): proposed to scale with the rest (a minute, then 3 a second). Unscaled, the failures of one QA
  run would pile up for an hour of real time in the same relay and tighten the later cases.
- Alternative with less to guard: reaching 20 failures takes two minutes at the real 10 a minute; only the 10-minute
  ban expiry needs a fast timer. QA-05 could shorten only the ban, or check the expiry in process with the
  injectable clock as `relay-server/test/ratelimit.test.ts` does.
- Architecture §9: replace "shortens TTL/heartbeat timers" with the chosen list.
- The server workstream implements it as plan task SRV-29 once the set is settled.
