# After a relay restart, WEB-14's code joins on new sockets meet the 30 upgrades/min limit (SRV-28)

- **Reported by**: server (`ws/server`, SRV-28)
- **Affects**: release — `docs/architecture.md` §8 T1 (the grace); web — WEB-14 (`web-viewer/src/protocol/reconnect.ts`, `CODE_FALLBACK_AT_MS`); qa — the
  "20 viewers, one address, relay restart" scenario (ADR 0008 classroom NAT)
- **Severity**: medium (NFR-20: a room of 20 behind one address may need ≈ 61 s instead of < 60 s to rejoin)
- **Milestone**: M2
- **Protocol**: v1.0 §9.2 (the code join on the `SESSION_NOT_FOUND` socket), §12 (30 upgrades/min per address)
- **Status**: open

## Steps to reproduce

1. 20 viewers behind one public address, a relay redeploy (§13 step 9).
2. Each viewer opens a socket for its token rejoin (`SESSION_NOT_FOUND`), then — WEB-14 as implemented — a new
   socket for each code join at ≈ 5, 15, 35 and 60 s.

## Expected

All 20 rejoin within 60 s once the presenter is back (NFR-20, ADR 0008).

## Actual

The relay is not banning the room any more: since SRV-28 failed joins in the first 120 s after a start do not count
towards the ban. But 20 token sockets plus 20 code sockets at ≈ 5 s are 40 upgrades from one address within a
minute; the relay allows 30 (§12), so 10 viewers get HTTP `429` at the upgrade and cannot connect until the window
rolls over: 20 token-rejoin upgrades at 0–3 s plus 20 code-join upgrades at 4–6 s (`CODE_FALLBACK_AT_MS[0]` plus
up to 2 s of jitter) are 40 within ≈ 6 s; refused upgrades are not recorded, so the window clears ≈ 60–63 s after the
token rejoins.

## Notes / suggested change

- WEB-14: send the first code join on the socket that got `SESSION_NOT_FOUND` — the relay accepts one code join there
  within a fresh 10 s window (SRV-15, report `2026-10-27-server-4` item 4). That halves the upgrades (20 + 20 retries
  later), and `test/restart-rejoin.test.ts` (relay) models exactly that client: no ban, all 20 join.
- A browser cannot read an upgrade `429` (it sees close `1006`), so WEB-14 retries on its backoff; the same-socket
  change above is the real fix (`retryAfterS` of `RATE_LIMITED` + `4006` is already honoured).
- Release (architecture §8, T1): add the exception to T1's controls/residual risk — for 120 s after a relay start
  failed joins do not count towards the ban (≈ 30 extra guesses per address per start, incl. `preferredCode` probes;
  the 10/min rate, the upgrade limit and the global alarm still apply).
- Relaxing the upgrade limit during the restart grace was not part of the accepted SRV-28 default; it would be a
  release decision (T3).
