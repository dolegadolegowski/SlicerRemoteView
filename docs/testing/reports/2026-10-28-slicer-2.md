# Resume (§4.3, §8.4): readings the slicer client relies on, and gaps around a relay restart

- **Reported by**: slicer (`ws/slicer`, SLC-17, on top of `6056785`)
- **Affects**: protocol — `docs/protocol.md` §4.3, §6.2, §8.4, §9.2, §13 steps 9–10; cc server (SRV-09, SRV-15),
  release, quest
- **Severity**: low (no contract change is asked for now; the client follows the readings below)
- **Milestone**: M2
- **Protocol**: v1.0, §4.3, §6.2, §6.3, §8.4, §9.2, §9.3, §13
- **Status**: open

## Steps to reproduce

1. Publish snapshot v1 (acknowledged), then begin snapshot v2; drop the connection before `scene.snapshot.end`.
2. Reconnect within grace and send `session.resume{lastSceneVersion: 2}`.
3. `tools/fake-slicer`'s relay stub answers `session.resumed{sceneVersion: 2, snapshotVersion: 1}`: it counts a
   `begin` as used. `ws/server` keeps begins apart (`registry.ts`: `sceneVersion` is the last accepted version,
   `lastSnapshotVersion` the last begun snapshot; `session.resumed`, SRV-15, is not implemented yet), so it may answer
   `sceneVersion: 1`. §4.3 does not say which.

## Expected

The protocol says when the publisher must re-send in terms the relay's answer can decide.

## Actual

§4.3 says "if `snapshotVersion` is `null` or older than the publisher's current scene, the publisher MUST send a new
snapshot". The slicer client reads it as follows (SLC-17, `remoteview_core/protocol_client.py` `resume_plan`):

1. A snapshot is owed unless `snapshotVersion` is the publisher's last acknowledged snapshot **and** `sceneVersion` is
   the publisher's last version.
2. §8.4 "continue from `session.resumed.sceneVersion`" is read as `max(ours, relay's)`, because §6.2 requires every
   `begin` above every version used so far.
3. The relay's `sceneVersion` may be a maximum over announced versions (the stub's reading, step 3 above), so
   equality with ours proves nothing about a snapshot cut by the drop. The client remembers the snapshot in flight at
   the drop: it is adopted when `snapshotVersion` names it (its ack was lost with the socket), and owed otherwise —
   correct under either reading. Suggest §4.3 to say which `sceneVersion` the relay reports. The relay's own check
   `begin > max(sceneVersion, lastSnapshotVersion)` (`ws/server`) is a further reason for item 2's `max`.
4. `error SESSION_NOT_FOUND` answering a resume cannot tell a wiped registry (a redeploy, §13 step 9) from a session
   that expired in grace (`PUBLISHER_GONE`, §9.1). The plugin re-creates with `preferredCode` only after a close
   `4008` in the same outage (SLC-45), so a relay crash without 4008 ends the session. Suggest
   `details.reason: "RESTARTED" | "EXPIRED"` on that error.
5. `session.resumed` carries no `limits` and no `platforms`; the client keeps the ones it had.
6. T4 after a restart: viewers saw the 4008 too and fall back to the code; whoever wins `session.create{preferredCode}`
   for the freed code gets them. A fallback create lost with its socket may leave an orphan session holding the code
   for its grace. (server, release)
7. §8.4 restarts versions at 1 after a fallback create: quest should key its GLB cache by `sessionId` + `sha256`
   (the web viewer resets on a new `sessionId`).
8. A fallback create refused with `RATE_LIMITED` ends the session (no retry loop in the plugin); several presenters
   behind one NAT after a restart hit the create limit — the relay could exempt `preferredCode` creates in the 10 s
   after a restart. (server)
9. SRV-15: how a `ping` in the 10 s fallback window after `SESSION_NOT_FOUND` is treated `[TODO verify]` (the relay
   stub drops the `session.create` that follows it).

## Notes / suspected cause

Items 1–3 are readings, not defects; items 4 and 6–9 are gaps for `protocol`, `server` and `release` to decide. The
client's tests pin each reading (`slicer-plugin/tests/test_protocol_client_resume.py`).
