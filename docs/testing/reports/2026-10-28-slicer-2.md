# Relay stub: what the resume tests reach into, and a fallback create it can drop

- **Reported by**: slicer (`ws/slicer`, SLC-39, on top of `e5dc31d`)
- **Affects**: protocol — `tools/fake-slicer/src/relay-stub.ts` (PRO-13); cc server (SRV-15)
- **Severity**: low (the slicer tests work around all of it; nothing is wrong for the stub's own tests)
- **Milestone**: M2
- **Protocol**: v1.0, §4.3, §9.1, §9.3
- **Status**: open

## Steps to reproduce

1. `slicer-plugin/tests/relay_stub.mjs` (slicer-owned wrapper) runs the stub for the slicer resume tests
   (`tests/test_resume_e2e.py`) and manual `docs/testing/slicer.md` §7. To report one entry per publisher handshake it
   replaces `stub.handshakes.push` and records `publisherFrames.length` at each call; to switch pongs at run time it
   mutates the options object passed to `startRelayStub` (the stub reads `options.answerPings` for every ping).
2. Start the stub with `publisherGraceMs: 50`, create a session and read `session.created.ttl.graceS`.
3. Answer a `session.resume` for an unknown session (`SESSION_NOT_FOUND`), then send a `ping` before the
   `session.create{preferredCode}` fallback on the same socket.

## Expected

1. A supported way to see where each publisher connection's frames start, and to switch pongs on and off.
2. `ttl.graceS` matches the grace the stub applies.
3. The fallback create is accepted after a `ping` too, as §4.3 keeps the socket open for it for 10 s.

## Actual

1. Both are internals: a change to how `handshakes` is filled or how `answerPings` is read breaks the slicer tests
   silently. Suggest `publisherConnections: {handshake, frames}[]` (or a handshake index on each recorded frame) and
   `setAnswerPings(on)`. `restart()` also returns nothing, so the wrapper cannot tell a restart from "no session".
2. `ttl()` always announces `graceS: 120` whatever `publisherGraceMs` is, so a publisher that sizes its reconnect
   window from `graceS` (the slicer plugin does, SLC-37) keeps trying after the stub's session is gone. Suggest
   announcing `ceil(publisherGraceMs / 1000)` when it is set.
3. After `SESSION_NOT_FOUND` the stub re-arms `onFirstMessage` once; a `ping` there is answered with
   `UNSUPPORTED_TYPE` and the following create is never read, so the publisher waits for its answer deadline. The
   slicer plugin sends the create in the same pump as the error, so its tests do not hit this, but a heartbeat due at
   that moment would. Suggest answering a `ping` there and re-arming, and that SRV-15 keep the socket unbound, with
   pings answered, for the whole 10 s window (the same question as `2026-10-28-slicer-1.md` item 9, now with the
   stub's behaviour).

## Notes / suspected cause

The slicer's wrapper (`slicer-plugin/tests/relay_stub.mjs`) works around item 1 (it reports one entry per handshake
from `handshakes.push` and switches pongs through the shared options object); item 2 does not affect its tests (the
panel's longer window only waits for an answer the stub gives at once); nothing in the stub is wrong for its own
tests. Line references: `tools/fake-slicer/src/relay-stub.ts` `ttl()` (`graceS: 120`), the ping handler
(`options.answerPings`), `handshakes.push` before the create or resume is handled, the single `socket.once` re-arm
after `SESSION_NOT_FOUND`, `UNSUPPORTED_TYPE` for a ping there, and `restart()` returning nothing.
