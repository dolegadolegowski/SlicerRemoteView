# Idle renewal: the client's `auto_renew` default

- **Reported by**: slicer (`ws/slicer`, SLC-47)
- **Affects**: release — `slicer-plugin/RemoteView/remoteview_core/protocol_client.py`
  (`ProtocolClient(auto_renew=True)` default); protocol — §4.4 (a warning repeated after `session.resumed`)
- **Severity**: low (the panel no longer relies on the default; the rest is wording)
- **Milestone**: M2
- **Protocol**: v1.0, §4.4; NFR-11; architecture §8 T1
- **Status**: open (item 1); item 2 answered by SRV-15 on `main`

## Steps to reproduce

1. Build `ProtocolClient(client_info)` with the default arguments, create a session and feed it
   `session.expiring{reason: "IDLE", closesAt}` every 29 minutes.
2. On `relay-server` with `SESSION_TTL_S=90`, create a session with no viewer, drop the publisher's connection about
   25 s after the idle period starts and resume it about 20 s later, after the warning fell due (30–40 s: the
   relay's sweep runs every 10 s).

## Expected

1. A client built without a policy does not keep a forgotten session alive (NFR-11, T1: the idle TTL shrinks the
   population of live codes).
2. A publisher that is back before the idle end hears that the session is about to end, so it can renew it (§4.4:
   "the publisher MAY answer `session.renew`").

## Actual

1. `auto_renew` defaults to `True`: every `session.expiring` is answered, so a session nobody watches lives until
   `SESSION_MAX_LIFETIME_S` (12 h) instead of the 30 min idle TTL. The panel no longer uses the default. Since SLC-47 it
   passes a callable that renews for one warning per Start, and only after a panel button was used within 5 minutes;
   otherwise the user gets *Keep session*. The default is `release`'s decision (SLC-06 review, branch audit). `False`
   would make a missing policy fail safe. The slicer workstream left it unchanged, as the plan asks.
2. Answered on `main` (SRV-15, report `2026-10-27-server-4` item 5). The relay repeats an outstanding warning (no viewer
   since, not renewed) right after `session.resumed`, with the same `closesAt`, also when the old socket got it
   (`relay-server/src/ws/publisher.ts`, `session.idleWarned`). The panel treats a repeat with the same `closesAt` as the
   same warning: after recent activity it renews it by itself — again, when its automatic renewal was lost with the
   connection — otherwise it offers *Keep session*; a later warning (a new `closesAt`) gets the offer once the automatic
   renewal of the Start is used (`test_panel_renew_the_warning_repeated_after_a_resume_is_the_same_warning`). What
   remains is wording: §4.4 does not say yet that the warning is repeated, or that a client treats a repeat with the
   same `closesAt` as the same warning (PRO-25's round 2 lists it).

## Notes / suspected cause

- The idle period restarts at creation, when the last viewer leaves and at each `session.renew`
  (`relay-server/src/registry.ts`, header comment). The panel clears its offer when a viewer joins and expects a new
  warning before a later expiry, which matches this.
- This report replaces the draft written during SLC-47 before `main` was merged. That draft asked the relay to
  repeat the warning, which SRV-15 already does.
