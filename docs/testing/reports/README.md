# Cross-component bug reports

A workstream that finds a bug in **another** component's code does not edit that component's plan
(`CLAUDE.md` rule 4). It files a report here instead; the owning workstream triages it at the start of
its next run (`CLAUDE.md` rule 9) and copies it into its own plan as a `todo` task.

## File name

`YYYY-MM-DD-<reporter>-<n>.md`, e.g. `2026-11-03-web-1.md` (`<reporter>` = component that found the bug,
`<n>` = running number for that day).

## Format

```markdown
# <one-line title>

- **Reported by**: <component> (`<branch>`, commit `<sha>`)
- **Affects**: <component> — <file or area>
- **Severity**: high | medium | low
- **Milestone**: M1
- **Protocol**: v1.0 (if protocol-related, cite the section of `docs/protocol.md`)
- **Status**: open | triaged (<task ID in owner's plan>) | fixed (<commit>) | rejected (<reason>)

## Steps to reproduce

1. …

## Expected

…

## Actual

…

## Notes / suspected cause

…
```

Reports never contain scene payloads, session codes or tokens (`CLAUDE.md` rule 6).

## Triage

The index of every report that still needs work is [`TRIAGE.md`](TRIAGE.md), generated by
`node tests/scripts/report-index.mjs` (Node 22, no dependencies). `node tests/scripts/report-index.mjs --check` exits 1
on a stale index or a report without an owner component or a status; it is meant for the CI lint job (to be wired by
`deploy`, DEP-10 — until then run it before committing a report). Regenerate it in the same commit that adds a
report or changes a `Status`; never edit it by hand.

### Who

- **Owner** = the first component named in `Affects` (a name from the `CLAUDE.md` component map: `protocol`, `server`,
  `web`, `slicer`, `quest`, `deploy`, `qa`, `release`). Further components in `Affects` are co-owners for their part;
  each records its own task ID in `Status` (`triaged (PRO-20; web/quest, 2026-10-27-protocol-3)`). Text that only
  `release` may change (`docs/architecture.md`, `docs/requirements.md`, `docs/plan/00-overview.md`, other workstreams'
  plans, `CLAUDE.md`) makes `release` the owner (`CLAUDE.md` rule 4).
- **The owning workstream triages** its reports at the start of its next run (`CLAUDE.md` rule 9): it reads
  `TRIAGE.md` (its section) and every report there with `Status: open`, copies each accepted one into its plan as a
  `todo` task and sets the report's `Status`.
- **The reporter** keeps the report factual and answers questions in it; it does not change the owner's plan or code.
- **`release`** checks before closing a milestone (`docs/plan/00-overview.md` §5 item 2) that nothing is left without an
  owner: `node tests/scripts/report-index.mjs --check --release` exits 1 while any report is still `open`, has no
  owner component or no status, or is `high` and neither `fixed` nor `rejected`. `qa` keeps the index and this
  process (`CLAUDE.md` rule 4 exception) and notes overdue reports (SLA below) in its run summary.

### When

| Moment | Who | What |
|---|---|---|
| A bug in another component is found | reporter | File `YYYY-MM-DD-<reporter>-<n>.md` (format above) with `Status: open`, run `node tests/scripts/report-index.mjs`, commit both. A system test that shows the bug stays in the suite as `test.fail` / `test.fixme` naming the report. |
| Start of the owner's next run | owner | Triage every `open` report of its section in `TRIAGE.md`: `triaged (<task ID>)` or `rejected (<reason>)`; regenerate the index. |
| Fix committed | owner | `fixed (<commit>)` in the same commit as the fix or the next one; the `test.fail` marker comes off with the fix (the test then passes). |
| Milestone merge (`release`) | release | `--check --release` green: no `open` report, no unfixed `high`. |

### Status transitions

```text
open ──► triaged (<task ID>) ──► fixed (<commit>)
  │              │
  │              └──────────────► rejected (<reason>)
  ├─────────────────────────────► fixed (<commit>)        (fixed before formal triage)
  └─────────────────────────────► rejected (<reason>)     (not a bug, duplicate, works as specified)
```

- `open` — filed, not yet looked at by the owner.
- `triaged (<task ID>)` — accepted; the task in the owner's plan is named (several IDs or a protocol decision such as
  `D5` are fine). A report split across owners lists each part: `triaged (PRO-20; web, WEB-31)`.
- `fixed (<commit>)` — the change is merged into the owner's branch; name the commit (and the task).
- `rejected (<reason>)` — the owner does not act; the reason is one line (duplicate of `<report>`, works as
  `docs/protocol.md` §x says, out of scope). The reporter may reopen it by setting `open` with a note.
- A report whose fix was reverted goes back to `triaged (<task ID>)`.

The index also reads the older words found in existing reports — `closed` / `done` / `resolved` as `fixed`,
`in progress` / `decided` / `accepted` as `triaged`, `wontfix` / `duplicate` / `invalid` as `rejected` — and lists them
as warnings so the owner can normalise them; new reports use only the four canonical words.

### SLA per severity

| Severity | Meaning | Triage | Fix |
|---|---|---|---|
| `high` | Security or medical-data exposure (`CLAUDE.md` rule 6, threat model), data loss, or a milestone DoD item / release check that cannot pass | Within **2 working days** (the owner's next run at the latest) | Before the **next milestone merge**; a milestone is not closed with an unfixed `high` report |
| `medium` | Wrong behaviour or a contract mismatch a user or another component can hit, with a workaround | At the owner's next run | Within the milestone named in `Milestone` (or explicitly moved to a later one with a note in the owner's plan) |
| `low` | Wording, documentation drift, test tooling, an unlikely edge case | At the owner's next run | Backlog: fixed when the owner next touches the area, or `rejected` with a reason |

A report past its SLA is not escalated automatically: `qa` lists overdue `high` and `medium` reports (by the date in
the file name) in its run summary, and `release` decides at the milestone merge.
