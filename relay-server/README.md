# relay-server — session codes, WebSocket relay, static web-viewer hosting (Node.js 22 / Fastify / ws)

Part of **SlicerRemoteView**. Owned by the `server` workstream (branch `ws/server`, plan
`docs/plan/server.md`). Contract: `docs/protocol.md`. Rules: `CLAUDE.md`.

## Purpose

The relay accepts one 3D Slicer publisher per session, hands out a 5-character session code, lets up to 20
viewers (web-viewer, Quest) join with it and forwards the scene to them. Everything is held in memory only
(single replica); nothing is written to disk and codes, tokens and scene bytes never reach a log. Design:
`docs/architecture.md` §3–§5, §8–§9; task list: `docs/plan/server.md`.

## How to run

From the repository root (Node 22, `npm ci` once):

```bash
npm run dev -w relay-server        # tsx watch, sources of shared/ via tsconfig paths, http://localhost:8787
npm run build                      # shared/ first, then relay-server/dist (and the other workspaces)
npm start -w relay-server          # node dist/index.js (needs the build above)
```

The relay listens on `0.0.0.0:$PORT`. For local work with the Vite dev server, allow its origin and turn off
proxy trust (nothing sets `X-Forwarded-For` locally):

```bash
ALLOWED_ORIGINS=http://localhost:5173 TRUST_PROXY=false npm run dev -w relay-server
cp relay-server/.env.example relay-server/.env    # or keep settings in a git-ignored .env …
node --env-file=relay-server/.env relay-server/dist/index.js   # … and load it with Node's --env-file
```

## Configuration

Environment variables (`src/config.ts`, same names as `docs/architecture.md` §9). Every value is validated at
start-up; an invalid one stops the process with exit code 1 and a `fatal` log line naming the variable (never
its value). Empty values count as unset. `relay-server/.env.example` lists exactly these variables with their
defaults (a test keeps both in sync).

| Variable                              | Default                            | Meaning                                                                                                                                                                                                                          |
| ------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PORT`                                | `8787`                             | listen port (Railway injects it)                                                                                                                                                                                                 |
| `LOG_LEVEL`                           | `info`                             | `fatal`, `error`, `warn`, `info`, `debug`, `trace` or `silent`                                                                                                                                                                   |
| `METRICS_TOKEN`                       | unset                              | Bearer for `GET /metrics` (≥ 32 printable characters, e.g. `openssl rand -base64 32`); unset disables `/metrics`                                                                                                                 |
| `SESSION_TTL_S`                       | `1800`                             | idle TTL while a session has no connected viewers (§4.4); at most the protocol value                                                                                                                                             |
| `PUBLISHER_GRACE_S`                   | `120`                              | resume window after the publisher's socket is lost (§9.1); at most the protocol value                                                                                                                                            |
| `SESSION_MAX_LIFETIME_S`              | `43200`                            | hard cap on a session's lifetime; at most the protocol value                                                                                                                                                                     |
| `CODE_QUARANTINE_S`                   | `600`                              | a released code is not reissued for this long (ADR 0008); at least `60`                                                                                                                                                          |
| `MAX_SNAPSHOT_BYTES`                  | `67108864`                         | per-snapshot cap, at most the protocol maximum (64 MiB)                                                                                                                                                                          |
| `MAX_TOTAL_SNAPSHOT_BYTES`            | `536870912`                        | cached + in-flight snapshots of all sessions; ≥ 2 × `MAX_SNAPSHOT_BYTES`                                                                                                                                                         |
| `MAX_TOTAL_BUFFERED_BYTES`            | `167772160`                        | Σ of all viewer send buffers (≥ 8 MiB, the per-viewer hard watermark); slowest consumers closed `4010` above it                                                                                                                  |
| `MAX_VIEWERS`                         | `20`                               | viewers per session, at most the protocol maximum (20)                                                                                                                                                                           |
| `MAX_SESSIONS`                        | `100`                              | live sessions (`CAPACITY` beyond)                                                                                                                                                                                                |
| `ALLOWED_ORIGINS`                     | `https://${RAILWAY_PUBLIC_DOMAIN}` | comma-separated browser origins allowed on `/ws` (exact match, no wildcards, `http:` only for `localhost`/`127.0.0.1`/`[::1]`); without both, only clients that send no `Origin` (Slicer, Unity)                                 |
| `TRUST_PROXY`                         | `true`                             | client IP = the `X-Forwarded-For` entry added by the immediate peer (Railway edge), never a client-sent one; `false` = socket address (direct local access). `true` assumes the relay is reachable only through the Railway edge |
| `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` | `30`                               | SIGTERM → SIGKILL window for the `4008` drain on redeploy                                                                                                                                                                        |

The three session timers are protocol maximums (§3.3, §14): a relay may run shorter, never longer.
`RELAY_TEST_FAST_TIMERS` is test-only: it is honoured only under `NODE_ENV=test` (SRV-21) and never set in
deployments. `NODE_OPTIONS` (`--max-old-space-size-percentage=75`, architecture §9) is set by the Dockerfile
(SRV-20) and read by Node, not by `config.ts`; `RAILWAY_PUBLIC_DOMAIN` is injected by Railway.

## HTTP endpoints

| Endpoint                              | Answer                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`/`HEAD /` and `/j`               | the web viewer's `index.html` (§10, ADR 0006), `Cache-Control: no-cache`; a query string changes nothing and is not echoed (the code travels in the fragment, `/j#CODE`)                                                                                                                                                                      |
| `GET`/`HEAD /assets/*`                | the viewer build's hashed files present at start, `Cache-Control: public, max-age=2592000, immutable`; a `.br`/`.gz` variant when present and accepted; anything else under `/assets/` → `404`                                                                                                                                                |
| `GET`/`HEAD /manifest.webmanifest`, `/icons/<name>.png` | the viewer build's web app manifest (`application/manifest+json`) and its PNG icons (`image/png`), `Cache-Control: no-cache`, looked up per request; `/icons/` accepts plain PNG names only (`[A-Za-z0-9][A-Za-z0-9_-]*.png`), anything else → `404` (SRV-26) |
| `GET /healthz`                        | `200 {"status":"ok","uptimeS":…,"sessions":…,"version":"…"}` — no codes, IPs or memory figures; `503 {"status":"draining",…}` once SIGTERM was received (SRV-17)                                                                                                                                                                                                                                                |
| `GET /api/version`                    | `200 {"name":"slicer-remote-view-relay","version":…,"protocolVersions":["1.0"],"limits":{…}}` (§10)                                                                                                                                                                                                                                           |
| `GET`/`HEAD /api/scene/:sceneVersion` | the cached GLB for `Authorization: Bearer <viewerToken>` (§10): `200 model/gltf-binary` with `ETag`, `X-Scene-Version`, `Cache-Control: private, no-store`; `401` no or unknown token, `404` other version or any query string/fragment/encoding in the target, `410` session ended (≤ `CODE_QUARANTINE_S` ago), `429` above 30/min per token |
| `GET /ws` (Upgrade)                   | WebSocket for both roles (§3): while the relay drains (SIGTERM) → HTTP 503 `{"error":"RELAY_RESTARTING"}`, before the per-address limit; more than 30 upgrades per minute from one client address → HTTP 429 `{"error":"RATE_LIMITED"}` with `Retry-After`; browser `Origin` must be in `ALLOWED_ORIGINS` (else HTTP 403), no `Origin` (Slicer, Unity) is fine; a `Sec-WebSocket-Protocol` offer is refused (HTTP 400); a plain HTTP `GET /ws` is a 404 |
| anything else                         | `404 {"error":"NOT_FOUND"}` — no SPA fallback beyond `/` and `/j`, the path is never echoed                                                                                                                                                                                                                                                   |

`GET /api/version` announces the effective `MAX_SNAPSHOT_BYTES` and `MAX_VIEWERS` (§14).

Every routed response carries `@fastify/helmet`'s headers (ADR 0006 §4); the 404s of URLs that do not decode and
the raw answers to unparsable requests do not. The CSP, as sent:

```text
default-src 'self';base-uri 'self';font-src 'self' data:;form-action 'self';frame-ancestors 'none';
img-src 'self' data: blob:;object-src 'none';script-src 'self';script-src-attr 'none';
style-src 'self' 'unsafe-inline';connect-src 'self' wss:;worker-src 'self' blob:
```

(one line; no `upgrade-insecure-requests`, so a plain-HTTP local run of the image works), plus
`Referrer-Policy: no-referrer`, `Strict-Transport-Security: max-age=31536000; includeSubDomains`,
`X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`. The viewer build lives in `relay-server/public/`
(`index.html`, `assets/`, `manifest.webmanifest`, `icons/`): a placeholder page is committed for development (`public/assets/*` is git-ignored) and the
Docker build puts `web-viewer/dist` there (SRV-20); during viewer development the Vite dev server serves it and
proxies to the relay (`web-viewer/vite.config.ts`).

Logs are JSON lines (`level`, `time`, `message`) on stdout; per-request logging is disabled. Lines carry session and
viewer ids, connection numbers, roles, sizes, durations, close and error codes and similar fixed values — never a
code, a token, a client address, a node name or scene bytes (`test/logs.test.ts` greps a whole session logged at
`trace`); `src/logger.ts` redacts code and token keys as a second line of defence. Two lines are there for the deploy
checklist (DEP-06): `relay starting` before the port is bound (`heapSizeLimit` from `v8.getHeapStatistics()`,
`maxTotalBufferedBytes`, `maxTotalSnapshotBytes`, `trustProxy`) and `first websocket upgrade` once with
`xff: "present" | "absent"`, `xffEntries` (the entries of `X-Forwarded-For`, the client's own included: read it from
a client that sends none, e.g. fake-slicer on a direct connection, as the first upgrade after a deploy) and the
HMAC'd `clientKey` — never an address. Memory figures are not on `/healthz` (SRV-19's `/metrics` will have them).

| `src/ws/snapshot.ts`   | snapshots (§6.1–§6.4). `scene.snapshot.begin` checks — `sceneVersion` a uint32 above every version used so far (`BAD_SEQUENCE`, which also discards a snapshot of that version in flight), `byteLength` above `MAX_SNAPSHOT_BYTES` → `PAYLOAD_TOO_LARGE` (also above the protocol maximum), `chunkCount = ceil(byteLength / chunkSize)` (`INVALID_MESSAGE`), cached + in-flight bytes of all sessions within `MAX_TOTAL_SNAPSHOT_BYTES` (`CAPACITY`, one `warn` per minute at most); a newer begin supersedes the snapshot in flight; the chunks of a refused version are ignored (a begin the schema rejects reserves nothing); one zero-filled buffer per snapshot, never pooled. Aborts (`SUPERSEDED`, `BAD_SEQUENCE`, `CHECKSUM_MISMATCH`, the publisher's own, `PUBLISHER_GONE`, `TIMEOUT` after 120 s without a chunk — the publisher also gets `BAD_SEQUENCE{chunkIndex, timeoutS}`) go to `SnapshotEvents`, like the accepted `begin`, chunks and `end` (`ws/fanout.ts`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `src/ws/budget.ts`     | per-socket message budget (T3, SRV-25): byte-weighted token buckets — text frames and client WS pings and pongs in one, a publisher's snapshot chunks in another — each frame charged its bytes plus its bucket's per-frame cost, so one 256 KiB frame weighs no less than 256 KiB of small ones; debt allowed down to one burst. Buckets (refill/s, burst, per frame): not yet bound 16 KiB / 512 KiB / 512 B, viewer 8 KiB / 64 KiB / 512 B, publisher 4 MiB / 4 MiB / 32 KiB (at most ≈ 128 frames a second — dispatch and fan-out —, while a 256 KiB update every 100 ms, §3.3/§8.1, never meets it), publisher chunks 32 MiB / 161 MiB / 16 KiB (two whole 64 MiB snapshots in 64 KiB chunks at once). Says per frame `ok`, `limited` (in debt, with `retryAfterS` covering the debt and one more small frame, and whether to warn: the first time and again once that time has passed) or `exceeded` (beyond a second burst); `endpoint.ts` acts on it. Binding gives the socket full buckets of its role. Refills on the injected clock (`budgets` option of `buildApp` for tests that flood).|
| `src/ws/state.ts`      | incremental updates (§8.1–§8.4): `scene.update`, `scene.nodeRemoved`, `scene.nodeAdded` from the session's own publisher socket. While a snapshot is in flight → `BAD_SEQUENCE{field:"snapshotInFlight"}` (ignored, §6.2); before the first snapshot → `BAD_SEQUENCE{noSnapshot}`; `baseVersion` ≠ the last accepted version → `BAD_SEQUENCE{baseVersion}`; `sceneVersion` not above it and every version a `begin` announced → `BAD_SEQUENCE{sceneVersion}`; above uint32 → `INVALID_MESSAGE`. These `BAD_SEQUENCE` answers are no strike towards `4007` (§9.2). Accepted: `sceneVersion` advances, `scene.update` merges only `visible`/`color`/`opacity`/`matrix` per node into `nodeState` (a removed node stays removed until the next snapshot), `scene.nodeRemoved` marks ids removed, `scene.nodeAdded` changes no state; the frame goes to every connected viewer byte for byte through the fan-out's `broadcast` (`ws/fanout.ts`). At most 1,000 node ids in the state (`MAX_STATE_NODES`, so `scene.state` stays ≤ ≈ 0.65 MiB; beyond → `BAD_SEQUENCE{nodeState}` until a snapshot empties it, T3). `sceneState()` builds §8.3's `scene.state` from `nodeState` (join, end-time `ready`, `scene.request`). Logs: session id, versions, counts at `debug`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `src/ws/fanout.ts`     | snapshot and update fan-out and the send buffers of viewers and publishers (§3.3, §6.4, §6.5, §9.3; architecture §4, §5). At an accepted `begin`, connected viewers whose `bufferedAmount` is below 4 MiB are streamed: the publisher's `begin`, chunks and `end` byte for byte, each chunk the same `Buffer` for every socket; the others, viewers that join mid-stream and streamed viewers at or above 4 MiB before a chunk get `scene.snapshot.ready` and then the empty `scene.state` (§8.3 b) after `end`, held to the limits below (the ack counts both). Aborts reach every viewer that got the `begin` (the publisher's own as received). `error SLOW_CONSUMER` + `4010` above 8 MiB, after more than 60 s at or above 4 MiB, or — largest buffer first, any session — when Σ `bufferedAmount` plus the next chunk would exceed `MAX_TOTAL_BUFFERED_BYTES` (a socket holding less than the chunk is not closed: a streamed one is deferred instead); a publisher's own socket is closed the same way above 1 MiB (it gets replies only, so all publishers hold at most `MAX_SESSIONS` × 1 MiB; logged as `PUBLISHER_LIMIT`); a closed slow consumer whose client does not complete the close is terminated after 5 s. While the sum (sockets it closed included, until they are gone) is at or above the budget, a publisher whose snapshot is in flight and whose streamed viewers hold its chunks is not read (`ws` `pause()`), at most 5 s at a time and then read for at least a second, so its pings are answered within 10 s (§9.1); every other publisher keeps being read. Joins get `CAPACITY` while the live buffers (without those it closed) hold the budget. Accepted updates (`broadcast`) are encoded once into one `Buffer` sent as a text frame (`bufferedAmount` then counts UTF-8 bytes) and held to the same limits before every send, but cannot be deferred: a viewer the frame would take above 8 MiB is closed `4010` instead, and for the budget the largest buffers, whatever their size, are closed until the sum plus the frame for every recipient fits. `deliver` holds the relay's own messages to one viewer (`scene.state` at a join, `scene.request` replies) to the same limits, each message encoded once; after `dispose()` nobody is closed, and messages go only to a viewer they leave within 8 MiB. A failing watch is logged (`INTERNAL`, no text) and keeps running. |
| `src/ws/heartbeat.ts`  | WebSocket-level heartbeat (§9.1, §9.3): a WS ping with a fresh random payload to every socket every 30 s; no pong echoing it by the next tick → close `4009` and terminated at once (at most ~60 s of silence; a publisher's session then enters grace). Unsolicited pongs and the client's own WS pings do not count. A missing pong is excused one interval at a time, the ping still outstanding (a late echo counts), while each interval shows another sign of life: a publisher sent a complete text or binary frame since the last tick (SRV-27: its pong may wait behind its own upload; paused by the fan-out or not — a viewer's frames do not count), or the socket's send buffer shrank; a socket without either, or an echo, is closed at the second tick (< 60 s). A socket no longer open whose peer started the close is handed to `close()` at the next tick, which drops it 5 s later unless its send buffer keeps shrinking (≤ 30 s, `Connection.close`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## Test and lint commands

```bash
npm test -w relay-server             # vitest (all relay tests)
npm test -w relay-server -- app      # one file by name filter, e.g. `app`, `config`, `codes`, `viewer`, `snapshot`, `state`, `late-join`, `fanout`, `budget`, `resume`, `shutdown`, `dispatch`, `http-scene`, `heartbeat`, `static`, `logs`, `e2e-fake-slicer`, `docker-smoke`
npm run lint -w relay-server         # eslint + prettier --check
npm run typecheck -w relay-server
npm run build -w relay-server        # tsc → relay-server/dist (needs `npm run build -w shared` first)
```

The root `npm test`, `npm run lint`, `npm run typecheck`, `npm run build` run every workspace.

The per-address limits (`src/ratelimit.ts`) also apply to E2E and load tests: from one address, more than 30
upgrades, 10 wrong codes or 5 sessions per minute are refused, and 20 wrong codes within 10 minutes ban it. Harnesses run the relay with `TRUST_PROXY=true`
and give each simulated client its own `X-Forwarded-For` address, as `test/ratelimit.test.ts` does.

## Test with fake-slicer

`test/e2e-fake-slicer.test.ts` (part of `npm test -w relay-server`, about 4 s) runs the relay in-process and
`tools/fake-slicer` (PRO-14…16) from its sources as a child process — `node --import tsx` on
`tools/fake-slicer/src/cli.ts` with `relay-server/` as working directory, so `shared` comes from its sources too (no
build needed); not `npx`/`npm run`, which do not pass fd 3 on. The session code comes only through `--code-fd 3 --json` (NFR-12; the test asserts that neither the code nor a
token or id is on stdout/stderr, without printing them). Two scenarios: a viewer that joins after `snapshot 1
acknowledged` fetches `GET /api/scene/1` with its token, and a viewer that joins before a second snapshot (a one-entry
`--script`) gets it streamed — decided by the viewer's own frames (`end`, not `ready`); both byte streams must match
`shared/fixtures/glb/manifest.json`, and `{"event":"viewer.count","count":1}` must reach fake-slicer's fd 3. By hand,
against a running relay (`npm run dev -w relay-server`), with the code written outside the working tree:

```bash
npm run build -w shared -w tools/fake-slicer
f="$(mktemp)"; echo "code file: $f"   # read it from another shell (cat "$f"), rm "$f" afterwards
node_modules/.bin/fake-slicer --relay ws://localhost:8787/ws --code-fd 3 --json 3>"$f"   # JSON Lines; Ctrl-C
```

## Docker

`relay-server/Dockerfile` (ADR 0007 §5), built from the repository root with the root `.dockerignore`:

```bash
docker build -f relay-server/Dockerfile -t slicerremoteview-relay:local .
RELAY_IMAGE=slicerremoteview-relay:local npm test -w relay-server -- docker-smoke   # skipped without RELAY_IMAGE
# Outside Railway there is no edge proxy in front: TRUST_PROXY=false, or clients choose their own address.
docker run --rm -e PORT=8787 -e TRUST_PROXY=false -e ALLOWED_ORIGINS=http://127.0.0.1:8787 \
  -p 127.0.0.1:8787:8787 slicerremoteview-relay:local   # http://127.0.0.1:8787/j
```

- Stage 1 (`node:22-alpine`): `npm ci` of all workspaces, `npm run build -w shared -w web-viewer -w relay-server`; the
  build fails if `web-viewer/dist` contains a symbolic link (the file server would follow it, SRV-16).
- Stage 2 (`node:22-alpine` + `dumb-init` as PID 1): `npm ci --omit=dev --ignore-scripts -w relay-server` (the
  relay's dependencies and the workspace links of `shared` and the relay only, 25 MB), `shared/dist`, `relay-server/dist`, and `web-viewer/dist`
  as `relay-server/public/`, all owned by root. It runs as `node` (uid 1000) from `/app/relay-server`,
  `CMD ["dumb-init", "node", "dist/index.js"]`, with `NODE_ENV=production` and
  `NODE_OPTIONS=--max-old-space-size-percentage=75` (the heap follows the container's memory limit: about 195 MiB at
  `--memory 256m`). No `EXPOSE`: Railway sets `PORT`.
- Docker Hub rate limits: pull the base from a mirror and tag it, e.g.
  `docker pull mirror.gcr.io/library/node:22-alpine && docker tag mirror.gcr.io/library/node:22-alpine node:22-alpine`.
- Build from a clean checkout: the root `.dockerignore` excludes `.env*` at the root only, so a `relay-server/.env`
  would reach the build stage (not the image; report `docs/testing/reports/2026-10-20-server-9.md`).
- Memory: the snapshot and send-buffer budgets (`MAX_TOTAL_SNAPSHOT_BYTES` 512 MiB, `MAX_TOTAL_BUFFERED_BYTES` 160 MiB
  by default) are `Buffer`s outside the V8 heap, which may grow to 75 % of the container's memory: size the container
  for both, or lower the budgets (same report).
